# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

YTAN is a web app for planning kayak touring trips (POIs, routes, tours, areas on a map). It's a from-scratch rebuild of an older app called PESR, structured so a future native mobile client can talk to the same backend. See `README.md` for the full "notable differences from PESR" list (REST API replacing a `service.php?cmd=...` RPC dispatcher, JWT bearer auth replacing PHP sessions, a path-traversal fix in `WsiRenderer`, etc.) and `docs/API.md` for the REST API reference.

## Tracking work (todo.md, done.md)

The repo-root `todo.md` is the running record of open feature work and notable pending fixes on this project — every new feature and every larger change must be noted there automatically, without the user having to ask. It holds only a single top-level `# Offene Punkte` section (open items, still pending), each its own `##` heading. The repo-root `done.md` holds the completed counterpart: a single top-level `# Erledigt` section, same one-`##`-heading-per-item convention. A still-open request stays under `todo.md`'s `# Offene Punkte`; once it's done, move its heading out of `todo.md` entirely and append it to the top of `done.md`'s `# Erledigt` section (don't leave finished work in `todo.md`, and don't leave a stale open item sitting in `todo.md` below one that's actually done). A closed item's body follows the existing style: the original request struck through (`~~...~~`) followed by `Gelöst (YYYY-MM-DD): ...` with a substantive explanation of what was actually built/fixed — not just "done", enough detail that the *why* and *how* survive independently of git history. (The two files used to be one, `todo.md`, with `# Erledigt` as its bottom section — split into `done.md` on 2026-09-21 to keep the still-open list short or grep it in isolation, so any workflow doc/memory referencing "todo.md's `# Erledigt` section" now means `done.md`.) A third file, the repo-root `future.md` (single top-level `# Zukünftige Ideen` section, same one-`##`-heading-per-item convention), holds deliberately deferred items - neither open nor done. Move an item there from `todo.md` only when the user asks, together with whatever has already been found out about it (findings, open questions), so that work isn't lost; once it's picked up again, it moves back to `todo.md`.

## Commands

```bash
composer install
cp .env.example .env              # fill in DB credentials, JWT_SECRET, MAPS_API_KEY, MAIL_*, APP_URL
php bin/migrate.php               # applies database/migrations/*.sql in filename order, tracked in a schema_migrations table
php -S localhost:8000 -t public public/index.php
```

- Adding a schema change: add a new plain-SQL file `database/migrations/NNN_description.sql` (zero-padded, next number) — there is no migration framework, just `bin/migrate.php` running un-applied files in sorted order once each. A data change plain SQL can't express can be a `NNN_description.php` instead, returning `function (PDO $pdo): void` (first one: `042_round_route_area_points.php`, rounds route/area `points` with `PointsJson::round()`, which `RouteRepository`/`AreaRepository` also apply on every save).
- No frontend build step — `public/js/*.js` are plain scripts loaded directly by `templates/app.php`, no bundler/transpiler/package.json.
- This machine has multiple PHP installs; the composer.json requires PHP >=8.1 but a plain `php` on PATH may resolve to an older 7.x build. Prefer an explicit 8.1+ binary (e.g. `/c/dev/php8/php.exe` on this Windows box) for anything version-sensitive (composer, migrations, `php -l`).
- When testing a UI/frontend change in a browser, always check the **mobile viewport first** (e.g. ~390×844), then desktop — this app is Mobile First (see Frontend architecture below), and mobile-only problems (touch targets too small, overlapping fixed-position elements, responsive fallbacks not kicking in) are easy to miss if desktop is checked first or exclusively.
- **Manual admin testing**: `/admin/*` pages (dashboard, users, settings, ...) need an admin login to get past their gate. A pre-seeded admin account for this — not created by any migration/setup script, already present in this dev DB — has its credentials in this machine's `.env` as `ADMIN_TEST_USERNAME`/`ADMIN_TEST_PASSWORD`; use it for browser-testing admin-only flows instead of creating a throwaway user (writing directly into the `user` table is easy to get wrong and isn't reversible the way a migration is).
- **Auto-generated build version**: `composer install`/`composer update` run `git config core.hooksPath .githooks` (a `post-install-cmd`/`post-update-cmd` script), which activates `.githooks/pre-commit` — a plain shell script (works under Git Bash on Windows too) that regenerates the repo-root `VERSION` file (`YYYYMMDDHHMM-<short hash of the parent commit>`, UTC) and `git add`s it into the very commit being made, every commit. `src/App.php`'s `/` route reads it (`$appVersion`, falls back to `'dev'` if the file is missing) and `templates/app.php` shows it in the nav drawer just under the Legal list. `VERSION` sits outside `public/` (never web-accessible, like `.env`) but isn't excluded from `bin/deploy.bat`'s upload package, so the deployed copy (no `.git` there) still has a real value to read. If you clone fresh and the hook doesn't seem to fire, re-run `composer install` or set `core.hooksPath` by hand.
- **Releasing an app version / in-app update**: `bin\build-app-release.bat` (signed release APK, JDK 21), then `bin\publish-app.bat` (production) or `bin\publish-app.bat test` — uploads the release APK to `public/app/ytan.apk` and only afterwards `public/app/version.json` (generated by `bin/app-version-json.php` from the APK itself via `aapt2`, not from `build.gradle`, which the pre-commit hook bumps ahead of what's actually built). Always the release APK: Android only installs an update over the same signing key. `public/app/` is gitignored and excluded from every deploy script, so deploys never clobber it. In the app, `public/js/native-app.js` compares `version.json` with the installed version (`AppInfoPlugin`) on every start and offers the update (banner + highlighted drawer row); `AppUpdatePlugin` downloads it (own server host only) and opens Android's installer. In a browser/PWA on Android the drawer shows "Install YTAN App" instead, hidden when `navigator.getInstalledRelatedApps()` reports the app (`site.webmanifest`'s `related_applications` + the APK's `asset_statements`).
- **Garmin watch data field** (`watch/`, Monkey C, Connect IQ): sideloaded, not in the Connect IQ Store. Build with `bin\build-watch.bat WATCH-KEY [DEVICE] [test]` (needs the Connect IQ SDK from Garmin's SDK Manager - located via `%APPDATA%\Garmin\ConnectIQ\current-sdk.cfg` or `CIQ_SDK_HOME` - and JDK 21; creates `%USERPROFILE%\.garmin\developer_key.der` with openssl if missing). The script writes the gitignored `watch/source/Config.mc` (server URL + the user's watch key from Profile > Garmin watch) and outputs `watch/bin/ytan-DEVICE.prg`, to be copied into the watch's `GARMIN\Apps`. Constraints that shaped it: a data field has no input UI (hence the baked-in key, `X-Watch-Token` instead of a JWT), may only fetch from its background process at most every 5 minutes, and can only hand a few KB from there to the foreground (hence `WatchRoutePayload`'s simplified flat integer list). `watch/` is excluded from all deploy scripts. `bin\build-watch.bat - DEVICE` rebuilds with the existing `Config.mc` (the watch key is only shown once in YTAN). `build-watch.bat` makes a **release** build (`-r`, ~11 KB instead of ~100 KB with debug info - data fields have little memory). `bin\sim-watch.bat [DEVICE]` builds a simulator-only debug variant (`watch/sim.jungle` → `watch/bin/simulator/ytan-DEVICE-sim.prg`, its own folder so it can't be copied to the watch by mistake), starts the Connect IQ simulator and loads it (works from cmd and PowerShell; `monkeydo` needs Java, the script puts JDK 21 on PATH). In that variant `YtanNavField.simulatedLocation()` (annotation `:simulator`; `monkey.jungle` excludes it, `sim.jungle` excludes the `:device` stub instead) fast-forwards a fake position along the real route when there's no GPS fix - the simulator has none by default. The manifest needs the `Positioning` permission, or `Activity.Info.currentLocation` is always null ("Kein GPS"). To test the sync against a local server in the simulator: point `watch/source/Config.mc` at it (restore it afterwards), switch off the simulator menu item Settings > "Use Device HTTPS Requirements" (otherwise plain-HTTP requests fail silently), and mind that the simulator remembers the last fetch - the immediate fetch at start only happens if 5 minutes have passed since, and a stored route from an earlier run is shown until then. Per-user settings reach the field through the same payload (`"c"` colors from Profile > Garmin watch, `"s"` default speed from Profile > Default speed) and apply without a rebuild. Besides that 5-minute fetch (and one at activity start, as early as Garmin allows), the YTAN **Android app** wakes the field right after a route is sent: `GarminWatchPlugin` (Connect IQ Mobile SDK, through Garmin Connect on the phone, app id = `watch/manifest.xml`'s id in dashed UUID form) sends a content-free `"sync"` message, `YtanSyncService.onPhoneAppMessage()` then does the normal fetch - so the server stays the only source of the route. JS side: `watch.js`'s `wakeWatch()` via `capacitor-bridge.js`'s `wakeGarminWatch()`, a no-op in a browser/PWA or on an APK without the plugin; nothing depends on it succeeding. **Without a key (Android app)**: since the watch key made every user/watch need its own build, the app can also send the route itself - `GarminWatchPlugin.send({payload})` puts the payload of `GET /watch/payload` (login, same `WatchController::payloadFor()` as the key-based `deviceRoute()`, same `"v"`) into the message, `YtanSyncService.onPhoneAppMessage()` hands a Dictionary with `v`/`p` on to `onBackgroundData()` unchanged (anything else, the plain `"sync"` of older apps, still means "fetch now"). `watch.js`'s `isWatchUsable()` (= key exists OR `watchDirectSend`, i.e. `CapacitorBridge.hasGarminWatchSend()` - `available()` rejects on an older APK) gates the watch controls instead of `isWatchPaired()` (key only), and `wakeWatch()` sends the payload whenever it can, falling back to the plain wake-up for a watch with a key. `bin\build-watch.bat app [DEVICE]` builds the key-less variant (`YtanConfig.WATCH_TOKEN` empty, `YtanKey.present()` false: no temporal event, no `makeWebRequest`, no "YTAN ?" sync label - one `.prg` per model for everybody); a build with a key does both (poll for the website/PWA, app messages without the app knowing the key). Caveat of the key-less variant: a data field only receives messages while it runs (activity started), so a route sent beforehand isn't delivered - the app's toast says so (`watch.route_not_reached`) and the watch keeps the last route in Storage. **Key without a build (`.SET` file)**: a data field has no file access (Connect IQ sandbox), but it reads its app settings (`watch/resources/settings` + `properties`: one string property `watchKey`) and `YtanKey.token()` prefers that over the compiled-in `YtanConfig.WATCH_TOKEN`. A sideloaded app's settings live in a binary file `GARMIN\Apps\SETTINGS\NAME.SET` on the watch, which can be replaced by hand - YTAN builds it: right after "create key" Profile > Garmin watch offers it (and keeps offering it until the next new key) as `ytan-ReplaceByWatchName.SET` (`GET /watch/settings-file`, `WatchController::settingsFile()`, `WatchSettingsFile::build()` - format reverse-engineered from files the watch itself wrote, `WatchSettingsFileTest` pins it byte for byte against a real one; Garmin doesn't document it). To keep it available the key is ALSO stored reversibly: `watch_link.token_enc` (migration 030), AES-256-GCM by `WatchKeyVault` with a key derived from `JWT_SECRET` (changing the secret makes older files unavailable until the next new key); the hash stays what the device endpoint compares. `bin\watch-key-file.bat KEY NAME` (`bin/watch-key-file.php`) does the same on the command line for a key you already have. So ONE key-less build per model plus a tiny `.SET` per user does the job. Gotchas found on a fenix 7X: the watch moves a copied `.prg` into internal storage (it vanishes from `GARMIN\Apps`) and keeps the NAME of the FIRST installation of an app id for its settings file (`ytan-fenix7pro.SET` although later builds were copied as `ytan-fenix7x.prg`), so NAME = the file the watch created in `SETTINGS` after the first start; the setting is read when the activity starts, so end the activity before swapping the file; a new key in YTAN invalidates the old one (the server stores only the hash), so a stale `.SET` shows "Watch key?" (401). **Memory decides which watches work** (`%APPDATA%\Garmin\ConnectIQ\Devices\*\compiler.json`, `appTypes`): the data field's limit includes the program itself (~22 KB release). Measured in the simulator with the route payload in Storage: on 32 KB devices (fenix 6 / 6S without Pro, Forerunner 245 without Music) it already runs out of memory in `initialize()`/`compute()` with a 10-point route (`System.getSystemStats()`: ~28.4 of 29.2 KB used) - those can't run it unless the field is slimmed down substantially, so Forerunner 245 Music (`fr245m`, 128 KB: ~51 KB used with a full 250-point route) is in `watch/manifest.xml` but `fr245` is not; `fenix6`/`fenix6s` are still listed although they hit the same wall. Devices with 128 KB or more (fenix 6 Pro family, fenix 7 family, fr245m; Venu 3S with 256 KB, added 2026-10-23) are fine. The Garmin Store isn't an option for now (it would allow app settings in Garmin Connect; the `.SET` file is the sideload equivalent). **Downloads for users**: `bin\publish-watch.bat [test]` builds the key-less variant for every product of `watch/manifest.xml` and uploads them with an `index.json` to `public/app/watch/` (like the APK: gitignored, excluded from deploys; the folder is replaced as a whole) - Profile > Garmin watch > "Datenfelder" (`watch.js`'s `showWatchDatafields()`, own drawer screen `watch-datafields`) lists them by model (display names from the SDK's `compiler.json`, `WatchDatafieldIndex`). A new model in the manifest = re-run it; a build is per host (server URL compiled in).
- **Watch simulator against the local server - pitfalls** (found 2026-10-10, each cost time): (1) the simulator needs `SERVER_URL` = plain `http://...` (nothing listens on 443 here) AND its menu item "Use Device HTTPS Requirements" OFF - **it is switched back ON every time the simulator process is restarted** (`sim-watch.bat` starts a fresh one if none is running), then the request is refused inside the simulator and never reaches Apache. (2) The simulator resolves `localhost` to IPv4 `127.0.0.1`, a browser/`curl` often to `::1`. On this box `127.0.0.1 pesr`/`kimai`/`kimaidev` in the hosts file plus `<VirtualHost pesr:80>` etc. used to make Apache bind those vhosts to 127.0.0.1:80 and answer everything arriving there (HTML 404 for `/ytan/...`, which Garmin reports as `YTAN -400` = "body not valid JSON"). Fixed in `C:\Apache24\conf\extra\httpd-vhosts.conf` (`<VirtualHost *:80>` for those three, backup `.bak-2026-10-10`; needs an Apache restart as admin); if `localhost` still 404s over IPv4 (`curl -4 http://localhost/ytan/public/api/v1/watch/device/route` should be 401), use the LAN IP in `watch/source/Config.mc`. (3) "YTAN ?" only means no fetch has finished yet; fetches then follow every 5 minutes. (4) To see whether the simulator really reached the server look at ALL of `C:\Apache24\logs\*access.log` - a request that hit the wrong vhost is in `pesr-access.log`, not `access.log`. (5) The device endpoint answers pure-ASCII JSON (`\uXXXX` instead of raw UTF-8), `WatchController::deviceRoute()`, as a precaution for Garmin's parser.

- **Scheduled cleanup task**: `php bin/cleanup-weather-data.php` deletes `weather_forecast` rows older than 7 days (todo.md's "Wetterdaten" item) — the first recurring/cron-style task in this project, so nothing invokes it automatically; add your own cron entry (or systemd timer) on each deployed host, e.g. `0 3 * * * /usr/bin/php /path/to/ytan/bin/cleanup-weather-data.php >> /path/to/ytan/storage/logs/weather-cleanup.log 2>&1`. A location's *previous* forecast is already deleted the moment a fresh one is fetched (`WeatherForecastRepository::upsert()`'s `ON DUPLICATE KEY UPDATE` on the `(lat, lng)` unique key) — this script only catches rows nobody has re-fetched at all, which would otherwise sit forever.
- **Rain radar job (third scheduled task, Python)**: `tools/radar/radar_job.py` (own venv `tools/radar/.venv`, see `tools/radar/README.md` for setup and the cron line - ONE entry, `tools/ytan_jobs.py` every 5 minutes, which runs this job and the wind job one after the other) fetches EUMETNET OPERA `DBZH` composites (1 km LAEA grid, read from each file - older docs say 2 km), computes a 2-hour nowcast (OpenCV optical flow + semi-Lagrangian advection; pysteps has no wheels and the production host has no compiler, no pip - venv via `--without-pip` + `get-pip.py`) and writes palette PNG tiles zoom 5-8 + `manifest.json` to `storage/radar/` (frames rendered by a process pool, number from the admin setting, `--workers N` overrides - fork on Linux shares the reprojection lookup, spawn on Windows rebuilds it per worker) (frames published by renaming a finished temp dir, immutable afterwards; it also deletes them). `RadarController`/`RadarTileService` serve them under `/api/v1/radar/` (must stay under `/api/`, `sw.php` caches other PNGs forever) and enlarge zoom > 8 from the zoom-8 tile, caching that inside the frame's own directory. Frontend `public/js/radar.js` draws the frames itself into ONE `<canvas>` (an `OverlayView` in the map pane) from preloaded, decoded `Image` objects, with a 350 ms crossfade - not with `ImageMapType`s: switching those by opacity flickered badly in the Android app (Maps sets the opacity on every tile `<img>`, Android Chrome decodes newly visible images asynchronously), and their `tilesloaded` event doesn't fire reliably. The view comes from `map.getBounds()`, not the overlay projection (stale right after a zoom); decoded tiles are pruned to the current view and the frames in use (256 KB each). No drawer switch: on/off via the map context menu item, off via the x on its panel; state `settings.detailradar`). **Admin page** (`/admin/radar`, own sidebar entry; `admin-radar.php`/`admin-radar.js`): settings = history 5-60 min, forecast 0-120 min, fetch interval 5/10/15 min (cron stays at 5, the job skips runs in between), parallel processes 1-12, regions (all European countries as boxes `RadarConfig::PRESETS` + own rectangles drawn on a map), stored in `app_settings` (migrations 043/044) and written to `storage/radar/config.json` for the job (`RadarConfig::writeJobConfig()`; the job has no DB access, `ytanradar/settings.py` reads it, defaults = DE/DK/SE + 120 min when the file is missing). The job renders the rectangle enclosing all regions and masks everything outside them (`Reprojector(regions=...)`; `max_mosaic_pixels` caps that rectangle - an admin setting since 2026-10-18, 50-500 M, default 120 M, memory ~8 bytes per pixel); a changed region set (`regions_hash` in the manifest) makes it delete and rebuild every frame. Spawned workers (Windows) must get the regions too - they build their own reprojector. **Missing radars**: not every country delivers every 5 minutes (8 of 10 Spanish radars are in every second OPERA composite only), which made the rain there halve and return every 5 minutes; the raw files keep the composite's radar list (`how/nodes`), and `Job.field()` (used for drawing, nowcast and verification - never draw from `load()` directly) fills a frame that lacks radars of the frame before from that one, moved on by one step, in the area that lost data plus 100 km (`nowcast.fill_missing_radars()`). `RENDER_VERSION` in job.py: bump it when the drawing changes, the job then redraws every frame once. Status: each run writes `storage/radar/status.json` (`Job.write_status()`: last run + outcome, last processing with download/processing phases, bytes, processes, total size of storage/radar), `RadarConfig::readStatus()` hands it to the page. Button "Jetzt aktualisieren": `POST /settings/radar/run` -> `RadarJobRunner` starts `radar_job.py --force` in the background (`setsid nohup ... &` on Linux, `start /B` on Windows) unless the job's lock `storage/radar/.lock` is held (PHP `flock()` sees Python's lock on both systems, checked); the page then polls the status every 4 s until the run is over, and checks every 15 s on its own (not in a background tab) whether a run - e.g. from cron - has started. **Pause**: 15/30/60 minutes or for good (`POST/DELETE /settings/radar/pause`, `app_settings.radar_paused_until` UTC / `radar_paused_forever`, migration 046, also in `config.json`); while paused the job does nothing (outcome `paused`) and "update now" is refused (409). Locally Apache runs as SYSTEM, so a job started from the local page creates files your user can't delete - test the button through `php -S` instead. Python tests: `tools/radar/.venv/Scripts/python -m unittest discover -s tools/radar/tests` - run them after changing anything in `tools/radar/`. `storage/radar` and `.venv` are excluded from all deploy scripts. Plan, measurements and decisions: `wetterradar.md`.
- **Wind layer (fourth scheduled task, Python)**: `tools/wind/wind_job.py` (runs in the rain radar's venv `tools/radar/.venv`, the only extra package is `imagecodecs`, see `tools/wind/README.md`; no cron entry of its own, `tools/ytan_jobs.py` runs it in the first tick of every quarter hour) fetches the DWD's ICON-D2 (0.02 degrees, +48 h) and ICON-EU (0.0625 degrees, to +120 h) `u_10m`/`v_10m` (optionally `vmax_10m`) GRIB2 files from opendata.dwd.de and writes them to `storage/wind/` as small fixed-grid blocks; it only works when a model run it hasn't processed is COMPLETE (`dwd.latest_complete_run()` reads the directory listings), otherwise it ends within a second ("unchanged"). **No eccodes**: it has no Windows wheel and pygrib has none at all, so `ytanwind/grib2.py` is an own ~100-line reader for exactly what the DWD files use (grid 3.0, packing 5.0 for ICON-D2 and CCSDS 5.42 for ICON-EU via `imagecodecs.aec_decode`, bitmap section 6) and refuses anything else loudly (traps: GRIB's E/D are sign-and-magnitude, `aec_decode` needs an output buffer LARGER than the data). Levels on one global grid (origin -90/-180, 129 x 129 points per block = 128 cells + the neighbour's first row/column so the browser never needs two blocks): L0 = whole area at 0.25 degrees in one file, L1 = ICON-EU blocks of 8 degrees, L2 = ICON-D2 blocks of 2.56 degrees (its edge, eroded 12 cells, and its bitmap holes are filled from ICON-EU); per point u, v [, gust] as bytes 0..254 on -40..40 m/s (gust 0..60), 255 = no data (outside the regions/model), gzipped by the job and served unchanged with `Content-Encoding: gzip` by `WindController`/`WindDataService` (`/api/v1/wind/manifest`, `/api/v1/wind/{run}/L0/{hour}`, `/api/v1/wind/{run}/{L1|L2}/{hour}/{bx}_{by}`; format in `docs/API.md` and `windkarte.md`). Publishing is atomic like the radar's (`runs/{runId}.tmp` renamed, `manifest.json` replaced, the replaced run stays 30 minutes). **Outside Europe: ICON global** (`ytanwind/icon_global.py`, 2026-10-19): when the cut area is not completely inside ICON-EU, the DWD's global model (icosahedral grid, template 3.101, ~3.5 MB per field, runs every 6 h, cell centres in the CLAT/CLON files) is regridded to 0.25 degrees with a cached nearest-cell index (`storage/wind/icon-global-index.npy`) and used as the LAST source in L0/L1/L2 (EU/D2 win where they have a value), first 72 hours only (`GLOBAL_MAX_HOURS`); an area outside ICON-EU downloads no EU files at all and the global run is the timeline (manifest `sources.eu` can be null, `sources.gl` is new; `wind.world` in config.json, default on, admin checkbox on /admin/wind, migration 049). Measured: ~530 MB per 72 h run, 30 s. **Own wind regions** (2026-10-19): `wind.regions` in config.json (`app_settings.wind_regions`, migration 050, `WindConfig::normalizeRegions()`; up to 10 rectangles anywhere on the globe, the whole world included - measured 2026-10-19 at 72 h: ~570 MB download, ~480 MB written, ~4.5 min -, drawn on a map on /admin/wind, button "Ganze Welt") replaces the rain radar's regions for the wind job; null = the radar's. The radar's own regions stay inside `RadarConfig::COVERAGE` (Europe). **The regions are the rain radar's by default** (`storage/radar/config.json`, `/admin/radar`) - one region choice for both overlays - but the job cuts the data to the ONE rectangle enclosing all regions, grown by `PAD_DEGREES` = 1 degree (`WindSettings.padded_regions()`): cutting to the single region rectangles left big holes over the sea between and beside countries (North Sea west of Denmark, Skagerrak - seen on a phone 2026-10-19) and empty strips at screen borders; the job-specific settings (forecast 24/48/72/120 h, process every 3rd/6th run, gusts, fine ICON-D2 grid, on/off - migration 047, `WindConfig`, `WindSettingsController`, own admin page `/admin/wind` with `admin-wind.js`, sidebar entry "Wind"; the colour fill's opacity is each user's own setting: slider in Preferences, `settings.windFillOpacity` in the settings cookie, default 40 %, read by `windFillOpacity()` in wind.js and applied live by `previewWindFillOpacity()`; it used to be a site-wide admin value, migrations 048/051) travel in the `wind` object of the same `config.json` (`RadarConfig::writeJobConfig()` takes it as a third argument - anything that rewrites that file must pass `SettingsRepository::windSettings()`, as `RadarSettingsController` does); switching the layer off deletes `manifest.json` (no manifest = "no wind data" in the app). "Update now" = `RadarJobRunner($root, 'wind')` (same lock-file check on `storage/wind/.lock`, log `storage/logs/wind.log`, error codes `wind.job_*`). **Frontend** `public/js/wind.js`: context menu item, state `settings.detailwind`, never on together with the rain radar (each `setXEnabled()` switches the other off, same panel spot, `#windControls` reuses the `.radar-controls*` classes). Cheapness is the design: the wind is sampled ONCE per map view (on `idle`) onto a coarse screen grid (8 px cells, `windRebuild()`), the per-frame particle step only reads that grid; ALL particles are ONE path with ONE `stroke()`, trails fade by one `destination-in` fill, 30 fps, canvas pixel ratio <= 1.5, 2,000 (phone) / 4,000 particles at most, the colour fill is drawn only on view/hour change at cell resolution and enlarged by the browser (CSS opacity 0.32, colours from weather.js's `windSpeedColor()`), animation pauses on drag/zoom/hidden page/open panel (`openPanelCount`) and stops after 60 s without map movement (time behind a full-screen panel does not count - `windFrame()` refreshes `windLastActivity` while `openPanelCount > 0`; a stop also CLEARS the particle canvas instead of leaving frozen trails; a map tap wakes it again). Particle speed is px per frame per m/s (not zoom dependent). Two canvases in one `OverlayView` in the map pane (pan with the map, re-placed on `idle`, and re-aligned in `draw()` via `windRealign()` when Maps re-bases the pane origin). **Fractional zoom trap (found on a phone 2026-10-19, wind drawn displaced against the map)**: after a pinch the map is drawn at a fractional zoom while `map.getZoom()` still answers a ROUNDED value (measured: `setZoom(6.63)` -> `getZoom()` 7, but the projection has 70.4 px/degree = 2^6.63), and `map.getBounds()` is computed for the rounded zoom too - so `wind.js` takes the scale from the overlay projection (`windProjectionScale()`) and anchors on `map.getCenter()`, never on `getZoom()`/`getBounds()`; the e2e test 'the wind sits where the map is, also at fractional zoom levels' pins it `radar.js` had the same problem (canvas and tile range from `getBounds()`/rounded `getZoom()`: at zoom 7.5 the canvas stopped 6 px short of the top and bottom edge and a tile column/row was missing) and now takes scale and zoom from the projection and the area from the map centre in `radarCurrentView()`, with `radar.spec.js` pinning it. **Rebuild timing (phone, 2026-10-19: a big part of the screen had no wind after panning)**: Maps' `idle` only comes once the tiles have loaded - seconds after a pan on a phone - and until then the canvases only cover the area they were built for (`WIND_MARGIN` = 128 px beyond the screen). So `windRebuild()` also runs `WIND_REBUILD_DELAY_MS` (150 ms) after the last `bounds_changed` (`windScheduleRebuild()`, not while a finger drags the map), not only on `idle`; a rebuild for a view/hour/run identical to the grid's own (`windGrid.key`) is skipped unless forced. A block that fails to load is NOT cached as "no data" (it is deleted from `windBlocks`) and the build is retried 3 s later, up to `WIND_BLOCK_RETRIES` times. **Never stuck (phone, 2026-10-19: after zooming in and out sometimes no overlay or no particles until a reload)**: a build is identified by `windViewKey()` (run, hour, centre, scale, size) and (a) a rebuild for the view the grid already shows aborts a build still in flight for another view (zoom out and straight back in used to let that build land with the wrong geometry), (b) a finished build whose view is no longer the current one is dropped and rescheduled, (c) a failing build calls `windRecover()` (fill visible again, retry) instead of leaving the layer hidden and stopped, (d) block requests time out after `WIND_BLOCK_TIMEOUT_MS`, (e) `windWatchdog()` (every 2 s) rebuilds when the grid has not belonged to the view for two checks in a row and restarts a stopped animation, (f) `windDragging` is cleared on `idle`/`zoom_changed` (a drag turned into a pinch never reports `dragend`). Gusts (only when `manifest.channels` is 3) only colour the fill (chip in the panel, `settings.windGusts`), particles always follow the mean wind. Tests: `python -m unittest discover -s tools/wind/tests` (synthetic GRIB2 messages of both packings, blocks, planning, a whole run against a fake DWD), PHPUnit `WindDataServiceTest`/`WindConfigTest`/`WindSettingsControllerTest`, e2e `tests/e2e/specs/wind.spec.js` (writes a tiny fixture into `storage/wind`, moving a real one aside for the run). **One cron entry for all jobs**: `tools/ytan_jobs.py` (every 5 minutes) takes `storage/.jobs.lock`, then runs the due jobs one after the other, each in its own process (`JOBS` there: radar on every tick, wind once per quarter-hour slot, decided from `storage/{job}/status.json` `last_run.start`; it passes `YTAN_JOBS_LOCK_HELD=1` so the children don't take the lock again). A job started by hand or from /admin/radar takes the lock itself (`wind_job.py` waits up to 6 minutes, `radar_job.py` skips its run), so the two never run together (the radar needs up to ~1 GB). There is NO separate wind cron entry; a new job = one line in `JOBS`. Tests: `python -m unittest discover -s tools/tests`. `storage/wind` is excluded from all deploy scripts. Plan, measurements, decisions: `windkarte.md`.
- **Water distance index** (`docs/water-index.md`): distances from a position to the nearest sea (`natural=coastline`), river/canal (centre line) and lake of at least 10 km² (shore, island rings included) come from ONE local file, `storage/water/water-index.bin`, read by `Ytan\Service\Water\WaterIndex`/`WaterDistanceService` in milliseconds (ring search over 0.05° cells, haversine on the nearest segment, > 100 km = null; OUTSIDE the countries' borders - `coverage` in `water-index.json`, Geofabrik `.poly` - no distances at all and nothing stored, `WaterDistanceService::covers()`, since without it a German harbour measured to the nearest Danish coast) - no Overpass/external request, so it runs on prod when a POI is saved. The shelter import (`shelter_import.sea_m/river_m/lake_m`, migration 057) computes them while staging (`ShelterImportRepository::upsertMany()`, unmoved entries keep theirs) and filters on them per kind; the old Overpass water check (`ShelterWaterCheckService`, 26 h for 31,000 entries) is gone. ## Testing

There is a real PHPUnit suite (`tests/Unit/`, `tests/Integration/`) backed by a **dedicated test database** — never the live one.

**One-time (or after a schema change) setup:**
```bash
composer test-db    # = php bin/setup-test-db.php
```
This clones the *structure* (no data) of whatever database your `.env`'s `DB_DATABASE` points at into a sibling `<name>_test` database (so `ytan` → `ytan_test`), then marks every migration file currently in `database/migrations/` as already applied there. It exists because `001_create_core_schema.sql` and a few other early migrations were deleted from the repo at some point (the live dev DB still has the tables they created; `bin/migrate.php` alone can no longer recreate them from scratch) — cloning the live structure sidesteps that gap entirely, whatever it currently contains becomes the test DB's baseline. Re-run it whenever the schema changes outside of a normal `bin/migrate.php` run picking up a new file for the test DB too (e.g. after a manual schema tweak, or to refresh the clone's baseline).

**Running the suite:**
```bash
composer test        # = phpunit, uses phpunit.xml + tests/bootstrap.php
```
`tests/bootstrap.php` loads the real `.env` for host/credentials but forces `DB_DATABASE` to `<name>_test` before anything else runs — even a buggy test can't reach the real database. `tests/TestCase.php` wraps every test method in a transaction that's rolled back in `tearDown()`, so tests never need their own cleanup and never see another test's leftover rows regardless of order; use its `createUser()`/`createRoute()`/`authPayload()` fixture helpers rather than hand-rolling inserts. Controller tests (`tests/Integration/ControllerTestCase.php`) call a `*Controller` method directly with a constructed PSR-7 request (`Slim\Psr7\Factory\*`) rather than going through Slim's router/`AuthMiddleware` — close enough to a real request for a controller's own logic (permission checks, validation, response shape), without a running HTTP server; an `ApiException` a controller throws propagates straight to the test, which is exactly what `expectException()` wants.

**This suite must be run after every change** (`composer test`), not just spot-checked manually — it already caught a real bug within minutes of being written (`TourRepository::setTags()`'s tag-casing dedupe kept the *last* casing seen instead of the documented *first*). When you add or change backend logic (a repository method, a controller endpoint, a permission rule), add or update a test for it in the same change — don't leave coverage for later. Manual/browser testing (see the mobile-first rule above) is still expected for anything UI-facing.

**Frontend end-to-end tests (Playwright)**: `tests/e2e/` is a self-contained Playwright project (its own `package.json`/`node_modules`, separate from both PHPUnit and the repo-root `package.json`'s Capacitor tooling) covering the frontend flows PHPUnit can't reach: login, POI/Route/Area creation via real map clicks, right-click context menus, and Tours (create + add a route). One-time setup: `cd tests/e2e && npm install && npx playwright install chromium`. Run with `npm test` (or `npm run test:headed` to watch it, `npm run test:ui` for Playwright's interactive UI mode).

- **Isolation from real dev data, and from PHPUnit's own `ytan_test`**: tests run against their own `ytan_e2e` database, created automatically on first run (`tests/e2e/seed/reset-e2e-db.php` clones it from `ytan_test`'s structure the same way `bin/setup-test-db.php` builds `ytan_test` itself) — never the real `ytan` dev DB, and deliberately **not** the same database PHPUnit uses either. `tests/e2e/server/e2e-router.php` is a router wrapper around `public/index.php` used only by `playwright.config.js`'s `webServer`, which forces `$_ENV['DB_DATABASE'] = 'ytan_e2e'` before `App::create()` ever runs. A plain OS environment variable override (`DB_DATABASE=ytan_e2e php -S ...`) does **not** work for this — verified empirically: `Dotenv::createImmutable()->load()` populates `$_ENV` from `.env`'s file value whenever `$_ENV` itself doesn't already hold the key, which is true here even when the OS env var is set (`getenv()` sees it, `$_ENV` doesn't, a `variables_order` quirk) — only setting `$_ENV` directly, before `Dotenv` runs, sticks. **Sharing `ytan_test` with PHPUnit was tried first and broke it**: leftover e2e-created rows (a POI landing on an auto-increment id a PHPUnit fixture inserts explicitly, an extra `user` row skewing `count()`-based assertions, `poitype` rows a fixture assumes don't exist yet) failed 12 PHPUnit tests the next time `composer test` ran - a completely separate database was the fix, not more cleanup logic.
- **Test user**: `tests/e2e/global-setup.js` runs `reset-e2e-db.php` once before the whole suite — upserts a fixed `e2e_test_user` (full rights, so the suite tests the *flows* rather than re-testing PHPUnit's own permission coverage), copies `poitype` reference rows from the real dev DB (schema-only clones have none), inserts the single default `app_settings` row (otherwise `SettingsRepository` prints PHP warnings above the page, which shifts the map and makes the pixel-offset clicks miss), re-clones `ytan_e2e` whenever its column layout differs from `ytan_test`'s (so new migrations reach it after `composer test-db`), and wipes anything that user created on a *previous* e2e run. It does **not** clean up between individual tests within one run — specs that need a guaranteed-empty patch of map to click on explicitly re-center there first (see below), rather than relying on the database being empty.
- **`fitToPoiBounds()` gotcha**: `map-core.js` unconditionally re-centers the map to `GET /pois/bounds` on load, which spans *every* POI in the database with no scope filter (`PoiRepository::bounds()` has no `WHERE`) — within a single e2e run this means "the center of the map" silently shifts depending on what earlier specs already created. `fixtures.js`'s `settleMapAt(page, lat, lng, zoom)` forces a known center/zoom (set twice, since `fitToPoiBounds()`'s own fetch can resolve after the first call and clobber it) — any spec that clicks the map at a fixed pixel offset must call it first, at coordinates not used by any other spec.
- **POI marker click offset**: a POI's marker (`YtanMarker`, marker.js) gets no `iconAnchor` for most types — the default anchor (AdvancedMarkerElement's, same as the old `google.maps.Marker`'s) is the *bottom-center* of the image, not its visual middle, so right-clicking exactly at a marker's `LatLng` pixel lands just below the icon on the empty map underneath (see `context-menu.spec.js`'s POI test, offset up by half the vendored icon's height).
- **Map click timing**: two `page.mouse.click()` calls fired back-to-back at different pixels can collapse into a Maps `dblclick` (which zooms instead of adding a second vertex) — `route.spec.js`/`area.spec.js` wait ~400ms between clicks so Maps' own click/dblclick disambiguation treats them as separate.
- **Desktop right-click, not the touch long-press path**: POI/Route/Area context menus register a native `contextmenu` listener directly (`poi.js`/`route.js`/`area.js`) *and* a separate touch-only long-press fallback (`attachLongPressContextMenu()`/`findLongPressTarget()` in `map-core.js`, for browsers where a long-press doesn't reliably translate to a `contextmenu` event) — `context-menu.spec.js` drives the former (`page.mouse.click(..., {button: 'right'})`), which is what a desktop user actually triggers; it doesn't exercise the touch fallback.
- Not yet covered: the touch long-press path itself, and cross-browser (only the `chromium` project is configured — add `firefox`/`webkit` to `playwright.config.js`'s `projects` if that coverage is ever needed).

## Backend architecture

- **Framework**: Slim 4, PSR-7 (`slim/psr7`). Everything is wired by hand in `src\App.php`'s `App::create()`, but lazily: repositories, services and controllers are registered as factories in a tiny PSR-11 `LazyContainer` (`$c->set(SomeController::class, fn ($c) => new SomeController($c->get(PoiRepository::class), ...))`, per-entity image stores as `'images.<entity>'`), routes are flat `$app->get/post/put/delete(...)` calls with `[SomeController::class, 'method']` (no route groups), and Slim resolves those through the container only when the route matched - so a request builds just what it needs. Only PDO, the Translator, `UserRepository`/`MailService`/`AuthService` (for `AuthMiddleware`) and the middlewares are built up front. A new controller needs a `$c->set()` entry; `AppWiringTest` fails for a route whose class has none.
- **Autoloading**: PSR-4, `Ytan\` → `src/`.
- **Request flow**: `public/index.php` → `App::create($rootDir)->run()`. `AuthMiddleware` runs globally and decodes a `Bearer` JWT (if present) into the PSR-7 request attribute `"auth"` — with the user claims (name, email, all rights) overwritten from the database on every request by `AuthService::authenticate()`, so a changed right/name or a deleted user applies immediately, not only after the token expires (`claimsFor()` is the one place that defines the claim shape) — it never rejects a request itself, so every route sees either a decoded payload or `null` there.
- **Controllers** (`src/Http/Controllers/*Controller.php`) extend `BaseController`, which provides:
  - `json($response, $data, $status=200)` — wraps success payloads as `{"data": ...}`.
  - `requireAuthUser($request)` — 401s if `auth` attribute is null, else returns the JWT payload array.
  - `requireAdmin($request)` — like above, plus 403s unless `is_admin` is true on the payload.
  - `assertOwnerOrAdmin($authUser, $ownerId)` — 403s unless the caller owns the resource or is admin.
  - `jsonBody($request)` — decoded JSON request body as an array.
- **Errors**: `src/Exception/*` (`ApiException` base + `NotFoundException`/`ValidationException`/`UnauthorizedException`/`ForbiddenException`) carry an HTTP status; the error handler registered in `App::create()` turns any thrown `ApiException` (or Slim's own HTTP exceptions) into `{"error": {"message": ...}}` with that status, plus a `trace` array when `APP_DEBUG=true` and the status is 500.
- **Data access**: `src/Domain/{Area,Poi,Route,Tour,User}/*Repository.php` take a raw `PDO` via constructor injection and use plain `prepare()`/`execute()`/`fetch()`/`fetchAll()` — no query builder/ORM. `Connection::fromEnv()` (`src/Database/Connection.php`) builds the PDO instance from env vars.
- **Auth/JWT**: `AuthService` (`src/Service/AuthService.php`) issues and verifies JWTs (`firebase/php-jwt`), holds the password policy (`validatePasswordFormat`), and login/self-change/admin-set/invite-token-redemption all funnel through a shared private `issueToken()` so the JWT claim shape (`sub`, `username`, `email`, `firstname`, `lastname`, `is_admin`, `tour_create`, `tour_publish`, `tour_manage`, `tour_copy`, `route_view_recording`, `export_routes_own`, `export_routes_public`, `tv`, `iat`, `exp`) stays consistent everywhere a token is minted. **Revocation**: `tv` = `user.token_version`; `authenticate()` rejects a mismatch, `UserRepository::bumpTokenVersion()` (password change/reset/admin-set, `POST /auth/logout-all`) invalidates every older token - anything that should "sign out everywhere" calls that. The signing key comes from `JwtSecret::key($_ENV['JWT_SECRET'])` (php-jwt 7 needs >= 32 bytes; missing secret = fatal, there is no fallback). `user_token.token` holds the SHA-256 of the mailed token, never the token. **Rate limits**: `RequestThrottle` (`auth_attempt` table) - login/forgot-password per identifier+IP, the anonymous weather/geocoding endpoints per IP (`hit()`); a new anonymous endpoint that costs an external request or a mail should use it too.
- **Granular Touren rights**: `user.tour_create`/`tour_publish`/`tour_manage`/`tour_copy` (flat boolean columns, same convention as `is_admin` — no permissions table) gate tour creation, publishing, managing any user's tours, and copying respectively; `is_admin` always overrides all four. `BaseController::assertTourRight($authUser, $right)` checks one; `TourController`'s private `assertCanManageTour()`/`assertCanPublishTour()` compose the "admin/tour_manage OR (owner AND the specific right)" rule used by update/delete/publish/route-membership/image endpoints. Granting/revoking happens in the admin user form (`admin-user.js`); `UserController::index()`/`UserRepository::findAll()` accept the same field names as exact-match query-param filters for the admin panel's filter chips. Because a partial `PUT /users/{id}` body must never blank out fields it didn't mean to touch, `UserRepository::update()` merges `$data` onto the existing row before writing (learned the hard way — an early manual test with a 2-field payload wiped a real user's name).
- **`route_view_recording` right**: same flat-boolean-column convention as the Touren rights above, but not a Touren right itself — it gates *visibility* of a GPS-recorded route's `recorded_at`/`recording_duration_seconds`/`recorded_by_username` (see `RouteRepository::SELECT_WITH_RECORDER`, a `LEFT JOIN user` for the recorder's username) rather than any action. `BaseController::hasRight($authUser, $right)` is the non-throwing counterpart to `assertTourRight()` — `true`/`false` instead of a 403 — for exactly this "redact a field, don't block the request" shape; `RouteController::redactRecordingInfo()` uses it on every response-producing endpoint (`index`/`show`/`create`/`update`) and fully `unset()`s the three keys rather than nulling them, so a caller without the right can't distinguish "not recorded" from "recorded, but hidden from you" — this applies even to the recording's own owner. `route.js`'s `showRouteInfoWindow()` mirrors the same check client-side (defense in depth: `saveRoute()`'s optimistic local route object still carries these fields in memory right after a save, before any server round-trip would have redacted them).
- **GPX export rights/setting**: `export_routes_own`/`export_routes_public` (same flat-boolean-column convention as `route_view_recording`, edited in the admin user form's "other rights" group) plus the site-wide `app_settings.gpx_export_public` switch (`/admin/settings`, `PUT /settings/gpx-export-public`, injected into the SPA as `window.YTAN_GPX_EXPORT_PUBLIC`) gate `GET /routes/{id}/gpx` and `GET /tours/{id}/gpx` - both in their own `GpxExportController` (it needs `SettingsRepository`, which `RouteController`/`TourController` don't) with the GPX itself built by `GpxExportService` (one `<trk>` per route, not `<rte>`, for import compatibility; a tour = one file with a `<trk>` per route in tour order, tour name/description in `<metadata>`). Rule, for a route or a tour as a whole: visible (route: public/own/admin; tour: public/own/admin/`tour_manage`, as `TourController::assertCanView()`) AND (setting on OR admin OR public + `export_routes_public` OR own + `export_routes_own`) - a tour's export then contains all its routes, its creator's private ones included, same as the tour PDF. `tour-admin.js`'s `canExportTour()` mirrors it for the tour detail screen's "Export GPX" button. `route.js`'s `canExportRoute()` mirrors it only to decide whether the route context menu shows "Export route (GPX 1.1)" - which is why `showRouteContextMenu()` now also opens for non-owners and signed-out visitors, with just that item plus Cancel.
- **Lazy POI/WSI markers (`LazyYtanMarker`, `marker.js`)**: `markers[id]` and `wsiMarkers[]` hold `LazyYtanMarker`s, not `YtanMarker`s - same surface (`setMap`/`getMap`/`position`/`icon`/`advanced`), but the Google marker (~130 µs each, the old cause of a multi-second load freeze on phones) is only built on `setMap(map)`/`.advanced`; `.real` is the built `YtanMarker` or null. Listeners and `attachLongPressContextMenu()` belong in its `onCreate(real)` callback (see `setPoi()`), since `findLongPressTarget()` and InfoWindow anchors need the real marker. Visibility is decided by `applyPoiTypeVisibility()` (type on AND inside the visible area + half a screen, re-run on every map `idle` from `POI_CLUSTER_ZOOM_THRESHOLD` up) - never loop over all POIs calling `setMap(map)`, that builds every marker. `poiHiddenForEditId` keeps an edited POI's original marker hidden. WSI icons are drawn client-side (`wsiSvgDataUrl()`, same geometry as `WsiRenderer`), not fetched from `/api/v1/wsi/{code}`.
- **Response compression and browser caching**: `CompressionMiddleware` gzips the app's own text responses (>= 1 KB, not `/watch/device/route`); `public/.htaccess` adds `mod_deflate` for static files and `Cache-Control: ... immutable` for every request with `?v=` (so always load scripts/styles/images in templates with `?v=<?= \Ytan\App::assetVersion(...) ?>`, or they only get the 1-day cache of unversioned images/fonts).
- **Map markers (`YtanMarker`, `public/js/marker.js`)**: every point marker (POIs, wind-shelter WSI icons, the POI being added/edited, the search result, the weather location) is a `YtanMarker` - a thin class around `google.maps.marker.AdvancedMarkerElement` (the deprecated `google.maps.Marker` is gone) that keeps the small slice of the old API the code uses: `setMap()`/`getMap()` (null when off the map), `getPosition()`/`setPosition()`/`position`, `setIcon(url)`/`getIcon()`/`icon` (`{url, anchor}`), `getTitle()`. It re-dispatches `gmp-click` and DOM `contextmenu`/`dblclick` (those two with `stopPropagation()`, so the map's own context menu/zoom don't fire too) as `click`/`contextmenu`/`dblclick` on itself, so `google.maps.event.addListener(marker, ...)` call sites stayed unchanged; handlers get `{latLng: marker position, domEvent}`. Differences to keep in mind: an InfoWindow needs `open({map, anchor: marker.advanced})`; icons are an `<img>` content element anchored bottom-center, a different `iconAnchor` (lighthouses: center, `poiIconAnchor()`) is applied as a CSS translate; the `<img>` must be `display:block` (inline left 3px of descender space and lifted every icon); a pin glyph must be an image URL (`glyphSrc`, see weather.js's SVG cloud) - `PinElement.glyph` with an element and `.element` are deprecated. - **Lighthouse duplicate check** (admin tool `/admin/lighthouse-duplicates`, `LighthouseDuplicateController`/`LighthouseDuplicateService`/`LighthouseDuplicateRepository`): finds lighthouse POIs within a configurable distance (default 50 m; latitude-sorted sweep + haversine, union-find so a chain of close lighthouses is ONE group - front/rear range lights also land in groups, so nothing is pre-selected) and merges the ones the admin ticks. Per group the tool shows one column per lighthouse (hand-drawn ones first - a `lighthouse_import.poi_id` pointing at a POI marks it "imported", the rest "manual" - since their positions are usually better); the admin ticks which are the same lighthouse, picks the record to KEEP (id, owner and photos stay) and per field (name, description, position = latitude+longitude, characteristic, sectors, international id, public) the record the value comes from; defaults: the first ticked record with a non-empty value. A switch (`hide_different_ids`) leaves out groups that contain an imported lighthouse and in which every lighthouse has an international ID but not all the same one (different lighthouses by the lists' own numbering); a group with any NULL/empty ID always stays. A second switch (`only_with_manual`) lists only groups in which at least one lighthouse was not imported; both filters run server-side before sorting/paging and combine. `merge()` updates the kept POI through `PoiRepository::update()`, copies the photos of the others to it (`ImageStorageService::copy()`, at most 5 in all - `MAX_IMAGES_PER_POI` mirrors `PoiController`'s), re-points `lighthouse_import` entries from the deleted POIs to the kept one (otherwise the FK's `ON DELETE SET NULL` would make them "open" again and importable twice) and deletes the others - all in one transaction per merge (copied files are removed again if it fails, the old files after the commit).
- **Tour tags/photos**: `tour_tag` (simple `tour_id`+`tag` join table, not a delimited string column) via `TourRepository::setTags()`/`getTags()`/`getTagsForTours()` (the last one bulk-fetches for list/search results, avoiding N+1). Photos (`tour_image` table + files under `storage/tour-images/{tourId}/`, outside the public webroot) go through `TourImageService` (validates real file bytes via `finfo`, not the client's claimed MIME type; max 5 MB, max 8/tour) and are served back through `GET /tours/{id}/images/{imageId}` after the same visibility check as the tour itself (public, owner, or admin/tour_manage) — never a static, guessable URL, since a photo can belong to a private tour. Because a private image needs the caller's Bearer token and a plain `<img src>` can't send one, the frontend fetches it as a Blob (`api-client.js`'s `fetchBlob()`) and sets `img.src` to an object URL (`tour-admin.js`'s `renderTourImage()`) instead of pointing `<img>` at the endpoint directly.
- **Tour route-change notifications & captcha-gated delete**: `RouteController::update()`/`delete()` look up affected tours via `TourRepository::findByRoute()` and recalculate each one's cached `total_length` (this is the *third* total_length trigger, alongside `TourController`'s own add/remove/reorder-route endpoints — a route's length changing via the normal route editor is easy to forget to wire up). `TourNotificationService` emails each affected tour's creator on change/delete (and the route's owner if a public route got deleted) via three new plain-text `MailService` methods, following the app's existing single-recipient `send()` pattern; every send is try/caught so a mail failure (e.g. no reachable SMTP in dev) never fails the underlying route update/delete. Deleting a route that belongs to ≥1 tours additionally requires a captcha: the first `DELETE` (no/invalid `captcha_token`+`captcha_answer` query params) throws `CaptchaRequiredException`, which `App::create()`'s error handler merges into the JSON error body as `tour_count`/`captcha:{question,token}`; `CaptchaService` signs the challenge as a JWT (reusing `JWT_SECRET`, since this stateless-JWT app has no PHP session to hold it server-side) scoped to `"route:{id}"` so it can't be replayed against a different route. Frontend: `route.js`'s `removeRoute()` catches the 422, shows `confirm-dialog.js`'s `showCaptchaDialog(question)`, and retries the same `DELETE` with the answer attached.
- **User invite / password-reset tokens**: `user_token` table (single-use, `purpose` = `invite` or `reset`, expiry-checked in SQL) backs both the admin-invite-new-user flow and "forgot password" — both resolve through the same `/set-password?token=...` landing page (`templates/set-password.php`), which is server-rendered (not part of the SPA) since it must work for a signed-out visitor arriving from an email link. `MailService` (`src/Service/MailService.php`, PHPMailer/SMTP) sends those emails; SMTP + `APP_URL` (needed to build absolute links outside of a request context) come from env vars.
- **HTTPS and security headers** live in `public/.htaccess` (301 to https except localhost/private IPs/dotless hosts, `nosniff`, `X-Frame-Options`, `Referrer-Policy`, HSTS on https only). They need `mod_headers`, which production has but this box's Apache doesn't load (`#LoadModule headers_module` in `C:\Apache24\conf\httpd.conf`) - so locally those headers are missing, that's expected. The **Content-Security-Policy** is NOT in `.htaccess` (a `Header set` there would replace it): `ContentSecurityPolicyMiddleware` adds it to every `text/html` response from PHP (`src/Http/ContentSecurityPolicy.php`: per-request nonce + `'strict-dynamic'`, no `'unsafe-eval'`, Google Maps hosts for img/connect/frame, `report-uri` = `POST /api/v1/csp-report` -> PHP error log, rate-limited), `.env`'s `CSP_MODE` = enforce/report/off.
- **Subdirectory deployment**: the app can be served from a path prefix (e.g. `http://localhost/ytan/public/`) instead of a vhost root. `App::create()` derives `$baseUrl` per-request from `$_SERVER['SCRIPT_NAME']` and calls `$app->setBasePath()`; that same `$baseUrl` is threaded into `templates/*.php` and injected client-side as `window.YTAN_API_BASE` (`public/js/api-client.js` reads it, falling back to `/api/v1`). Don't hardcode absolute paths in templates/JS — always go through `$baseUrl` / `window.YTAN_API_BASE`.

## Frontend architecture
- Mobile First
- Plain ES6, no bundler. `templates/app.php` loads vendor libs then `public/js/*.js` in a fixed, load-order-dependent `<script>` sequence (`config.js → helper.js → api-client.js → settings.js → ui.js → toast.js → confirm-dialog.js → nav-menu.js → map-core.js → poi.js → route.js → area.js → tour.js → tour-admin.js → user.js → admin-user.js`) — later files rely on globals (`log`, `LOG_ERROR`/`LOG_WARN`/`LOG_INFO`/`LOG_DEBUG`, `user`, `map`, `settings`, `Ytan`, etc.) defined by earlier ones, and most functions are attached implicitly to `window` rather than namespaced.
- **URL parameters (shared links)**: the SPA's address bar is kept clean. A small inline script at the top of `templates/app.php`'s `<head>` moves EVERY query parameter of the page URL (`tour`, `route`, `z`, `lat`, `lng`, and any added later) into `sessionStorage['ytan_pending_link']` (JSON object) and removes them from the URL with `history.replaceState()` before anything is shown; `map-core.js`'s `linkParam(name)` reads them (falling back to `ytanUrl.searchParams` when storage is unavailable) and `initMap()` deletes the stored copy so a reload doesn't replay it. **A new URL parameter therefore needs no change in `app.php` - just read it through `linkParam()`, never `location.search`/`ytanUrl` directly** (they no longer contain it). Link builders (`shareMap()`/`shareTour()`/`shareRoute()`) are unaffected - they build absolute URLs themselves.
- **No inline JavaScript (CSP)**: every `<script>` tag in a template needs `<?= \Ytan\Http\ContentSecurityPolicy::nonceAttr() ?>` (scripts that a nonced script creates itself, e.g. the Google Maps loader, are trusted via `'strict-dynamic'`). Event handlers are never `onclick="..."`/`oninput=...` & co. - write `data-on-click="fn(1, 'x', this, event)"` (also `data-on-input/change/submit/keypress/keydown/pointerdown`; add a type to `EVENTS` in `public/js/csp-events.js` if you need another). `csp-events.js` (loaded first on every page) handles them with one capture-phase listener per type and PARSES the calls, no eval: only global, non-native functions (top-level `function x()` or `window.x = ...` - NOT `let`/`const` objects, no dotted names, no assignments; wrap those in a small top-level function like `myPositionRemove()`), arguments only literals, `{key: literal}`, `this`, `this.value/.checked/.dataset.x`, `event`; `return false` = `preventDefault()`. Inside a handler `event.currentTarget` is the document - use `event.target` / `this`. Helpers there: `clickElementById(id)`, `navigateTo(url)` (own origin only), `printPage()`. `NoInlineScriptTest` fails on an inline handler, a nonce-less script tag or a `javascript:` URL; the e2e `page` fixture fails a test on any CSP violation or refused `data-on-*` call in the console. Native app: Capacitor injects its bridge via `addDocumentStartJavaScript` (outside the CSP); the old-WebView proxy fallback serves the HTML without the server's headers.
- **User text in HTML (XSS)**: everything a user (or OSM/NGA data) can write goes through `helper.js`'s `escapeText()` (names etc., decodes PESR-era entities first), `escapeHTML()`, `safeUrl()` (hrefs, http(s) only) or `renderMarkdown()` (descriptions: `marked` + DOMPurify with `ALLOW_DATA_ATTR: false` - a `data-on-click` from user Markdown would be run by csp-events.js; vendored in `public/lib/dompurify/`) before it reaches `innerHTML`/`setContent()`/an attribute - never `marked.parse()` or a raw `+ poi.name +`. `t()` interpolates its vars unescaped, so escape a user value before passing it in when the result becomes HTML. A self-made escape helper must escape quotes too (`textContent` -> `innerHTML` does not). Read endpoints (`show()`, `?tour_id=`) apply the same visibility rule as the photo endpoints and answer 404 for a record the caller may not see (`VisibilityTest`).
- **API access**: all backend calls go through the `Ytan` singleton (`public/js/api-client.js`): `Ytan.get/post/put/del(path[, body])`, `Ytan.isLoggedIn()`, `Ytan.setToken/getToken` (JWT kept in `localStorage['ytan_token']`, not a cookie). Don't `fetch()` the API directly from feature code.
- **Session bootstrap**: on page load (`templates/app.php`'s inline `<script>`), `user` is set to `initUser()`'s empty shape first, then — if a token exists — revalidated against `GET /api/v1/auth/me` (rather than trusting a cached `sessionStorage['user']` blindly) before the UI reflects logged-in state.
- **Navigation drawer** (`#sidemenu`): a hamburger-toggled drawer. Opening and closing use two separate, differently-positioned buttons, matching the approved mockup: `#sidemenu-toggle` (fixed top-left, always shows the `menu` glyph, calls `toggleMenu()`) sits outside the drawer and only opens it; a `.nav-close-x` button lives *inside* the drawer's `root` screen (`.nav-brand-row`, pushed to the row's right edge via `margin-left:auto`, next to the "YTAN" wordmark) and only closes it. `#sidemenu`'s z-index (11) is deliberately higher than `#sidemenu-toggle`'s (10) so the open drawer visually covers the hamburger button instead of the two overlapping — don't reintroduce an icon-swap or reposition the toggle to "fix" that overlap, the z-index order is the fix. Only the `root` screen has a close-x; submenu `.nav-screen`s rely on their own `arrow_back` button instead. The drawer itself contains a stack of `.nav-screen` panels (`public/js/nav-menu.js`: `navMenuGoTo(screenId)`/`navMenuBack()`/`navMenuReset()`) that slide horizontally instead of one flat list. Screens are matched by `data-nav-screen="..."` in `templates/app.php`; closing the drawer resets the stack back to `root` (delayed until `#sidemenu`'s own 0.5s slide-out transition finishes, so the reset is never visible mid-close). Map type/units/POI-visibility checkboxes/tour selector all kept their exact IDs when they moved into this structure (`settings.js`'s `saveSettings()`/`loadSettings()` and a couple of direct references in `area.js`/`route.js` read them by hard-coded `getElementById`, independent of DOM position) — never rename `detail0`-`detail16`, `detailroutes`, `detailareas`, `detailwsi`, `maptype1`-`maptype3`, or `unit1`-`unit2` without updating those too. The `pois` screen also has `selectAllPois()`/`selectNonePois()` (`map-core.js`) wired to a `.nav-quick-actions` chip pair. The `preferences` screen holds both the Appearance (Light/Dark, `setTheme()`) and Units (Metric/Nautical, `editUnit()`) segmented controls, one above the other — Units used to be its own `map-settings` screen but was folded in here since both are simple app-wide toggles; it also shows a live-updating `.nav-example-card` (`updateUnitExample()`, `map-core.js`) that mirrors the current unit choice, right below the Units control. The login/logout/change-password UI lives inside this same `preferences` screen — `showUserWindow()`/`closeUserWindow()` (`user.js`) call `navMenuGoTo()`/`navMenuBack()` instead of toggling their own visibility. The admin user-management UI does **not** live in the drawer — see the full-screen panel below; the drawer's `site-settings` screen just has a single "Users" row that opens it via `openUserAdminMenu()`.
- **Full-screen overlay panels** (cookie consent, Impressum/Datenschutz, admin user management, the Tours panel): all four share one CSS pattern — a `<div class="cookiemenu">` slid in via a `style.width` transition (`0` ↔ `100%`), plus a matching `openXMenu()`/`closeXMenu()` JS function pair (see `openCookieMenu`/`openLegalMenu` in `public/js/ui.js`, `openUserAdminMenu`/`closeUserAdminMenu` in `admin-user.js`, `openTourAdminMenu`/`closeTourAdminMenu` in `tour-admin.js`). The admin panel is triggered from the drawer's "Site Settings" screen but is deliberately its own full-screen panel rather than a nested `.nav-screen` — a data table doesn't fit the ~320px drawer width — so `openUserAdminMenu()` calls `closeMenu()` first for a clean transition. `openTourAdminMenu()` (triggered directly by the drawer root menu's "Tours" row — unlike POIs/Preferences there's no intermediate `.nav-screen` for it; the old in-drawer tour-picker dropdown that used to live there was removed as obsolete once this panel could do everything it did, and `openTourAdminMenu()` calls `closeMenu()` itself, same as `openUserAdminMenu()`) follows the same pattern, swapping its single `#touradminmenu-body` container's content between four sub-views — list/search (name/description/creator text search plus a length-range filter, all client-side over the already-loaded `tourAdminAllTours`), detail (tags, photo gallery, routes, and an action row whose buttons are individually gated by `canManageTour()`/`canPublishTour()`/`canCopyTours()`; a "Share" button sits alongside them, gated on `tour.public == 1` instead since `TourController::show()` has no `assertCanView()` of its own the way `showImage()`/`document()` do — `shareTour(id, name)` mirrors `map-core.js`'s `shareMap()` Web Share API/clipboard-copy pattern, building a `?tour={id}` link that `initMap()` reads the same way it already reads `z`/`lat`/`lng`, fetching the tour directly and calling `tour.js`'s `activateTourMode()` once the map is ready — or a `showToast()` notice if the tour 404s, e.g. deleted or made private since the link was shared), create/edit form (name/description/tags always; a photo upload grid only in edit mode, since a tour needs an id before it can own photos), and a route-membership manager ("Option B" from the Touren feature design: a searchable checklist of the user's own routes, with an "in this tour" section reordered via up/down buttons rather than drag-and-drop) — the same way `admin-user.js` swaps `#useradminmenu-list`/`#useradminmenu-form`. The "New tour" button and the map InfoWindow popup's "+ New tour…" shortcut (`route.js`) are both gated on `canCreateTours()`. `openCookieMenu()`/`openLegalMenu()` do the same for the same structural reason: `#sidemenu`'s z-index (11) sits above `.cookiemenu`'s (10) so the drawer, if left open, visually covers whatever panel opens on top of it — every "open a full-screen panel from inside the drawer" trigger must call `closeMenu()` first, not just the admin one. Every open/close call also goes through the shared `panelOpened()`/`panelClosed()` counter in `ui.js`, which hides `#editToolbar` (it visually sits above these panels) while any panel is open — use that pair rather than toggling it directly, since the counter is what keeps two panels opened back-to-back from clobbering each other's close. Each panel also ends its own `.cm_content` with a `<div class="panel-logo">` — deliberately a normal flow element, not `position: fixed`, since a fixed logo stays pinned to the same screen position for as long as the panel is open and covers whatever content scrolls underneath it, not just content past the very end. New panels should follow this same pattern (including their own trailing `.panel-logo`) rather than introducing a new one. `.panel-logo` and `.logo_large` (the same YTAN mark shown on the pre-consent GDPR screen) are empty `<div>`s, not `<img src="images/ytan.svg">` — the SVG is applied via `mask-image` with `background-color: var(--color-text)`, the same technique used for the Google InfoWindow close button's icon (see the "Google Maps InfoWindow chrome" block in `style.css`). This lets the logo, which is pure hardcoded black inside the SVG file itself, follow the theme instead of staying invisible on a dark panel. Because a `<div>` has no intrinsic size the way an `<img>` would, both classes set an explicit `aspect-ratio` matching the SVG's own `viewBox` (1873/1349) — don't drop that when touching either rule, or the mask collapses to zero height. `#legalmenu` (the Imprint/Privacy Note panel) is shared by a third row too: "About" (right above Imprint in the drawer's footer list) calls the exact same `openLegalMenu('<baseUrl>/about')`/`closeLegalMenu()` pair, fetching `templates/about.php` via the `/about` route (`src/App.php`) the same way `/legal/impressum` and `/legal/datenschutz` serve their templates — no dedicated JS function or panel of its own. Its content is the text that used to sit as a plain `#disclaimer` block at the bottom of the root menu screen. Follow this pattern (a new `templates/*.php` + route, opened via the existing `openLegalMenu(url)`) for any other static text that belongs alongside Imprint/Privacy Note, rather than special-casing the panel.
- **Dark mode / design tokens**: `public/css/style.css` defines its palette as CSS custom properties on `:root` (light) and `:root[data-theme="dark"]` (dark) — `--color-bg-panel`, `--color-text`, `--color-accent`, etc. Every color in the stylesheet should go through one of these tokens rather than a literal, or it will only render correctly in one theme. The active theme is `settings.theme` ('light'/'dark'), persisted through the same settings-cookie mechanism as `maptype`/`unit` (cookie `ytan_settings`, `path=/`; until 2026-10-16 it was `settings`, which other apps on a shared host such as the dev box's `localhost` overwrote - `readSettingsCookie()` still falls back to an old `settings` cookie that looks like YTAN's, never deletes it; `templates/help.php` and `Translator::resolveLocale()` read the same cookie) (`saveSettings()`/`loadSettings()` in `settings.js`), applied via `document.documentElement.dataset.theme` by `setTheme()` (`map-core.js`, next to `editMapType`/`editUnit`) and switched from a segmented control in the "Preferences" drawer screen. `applyStoredTheme()` (`settings.js`) is called as the very first thing in `templates/app.php`'s inline bootstrap script, before Google Maps even starts loading, so a returning dark-mode user doesn't see a flash of the light theme. The standalone pages (`impressum.php`, `datenschutz.php`, `set-password.php`, `forgot-password.php`) load the same `style.css` and so get the light palette automatically, but have no theme-switch UI of their own — out of scope by design, they're not SPA screens. CSS custom properties can't be substituted inside a `url()` data-URI's own content (see `.select-css`'s dark-mode arrow icon override) — those need a full second `background-image` declaration with the color hardcoded, not a `var()` inside the SVG string. The Route/POI/Area edit dialogs (`.infoWindowElement`, opened via `google.maps.InfoWindow`) are a second exception: Google renders the bubble chrome itself (background, tail, close button, scrollbar) via its own stylesheet injected at runtime (`.gm-style-iw-c`, `.gm-style-iw-tc::after`, `.gm-ui-hover-effect span`), completely outside our `--color-*` cascade — our own markup inside the bubble already picks up the right tokens, but the chrome around it stayed hardcoded white until explicit `:root[data-theme="dark"] .gm-style-iw-c { ... !important }`-style overrides were added (see the "Google Maps InfoWindow chrome" block in `style.css`, right after the MeasureTool section). `!important` is required there since Google's rules load after ours. If a future Maps API version renames these classes, that block is the place to fix it.
- **Fonts**: self-hosted (`public/fonts/`, declared in `public/css/fonts.css`) — Plus Jakarta Sans (body, replaces the old Roboto) and Sora (headings/brand, replaces the old Roboto Condensed), both fetched from Google Fonts once and vendored the same way `MaterialIconsRound` already was (no Google Fonts CDN requests at runtime, matching the "everything local" approach). `--font-body`/`--font-display` custom properties point at them. A third, Barlow Condensed (600 only, `--font-condensed`), is vendored the same way for the weather timeline's narrow wind-direction abbreviations (they have to fit a 22px chip).
- **Icon font**: `.material-icons-round` uses a vendored, older/classic Material Icons glyph set (`public/fonts/MaterialIconsRound-Regular.*`), not the newer Material Symbols set — some newer icon names (e.g. `key`, `route`, `pentagon`, `polyline`, `hexagon`) don't exist in it and silently render as nothing (no visible glyph, no error). When adding an icon, verify the ligature name is actually present in the vendored font rather than assuming current Material Symbols naming. The mockup itself isn't a reliable source for ligature names either — it renders icons with "Material Symbols Rounded" pulled live from Google Fonts, a different (larger, newer) font the app deliberately doesn't depend on at runtime (see "everything local" below).
- **`#editToolbar`'s three create-buttons** (`routeButton`/`poiButton`/`areaButton`) are the one exception to the icon-font approach above: they render the mockup's exact `route`/`add_location`/`pentagon` Material Symbols Rounded glyphs as inline `<svg viewBox="0 -960 960 960"><path fill="currentColor" .../></svg>` markup directly in `templates/app.php`, not via the vendored icon font (`route`/`pentagon` don't exist there — see above). `fill: currentColor` on `.toolbar-icon-btn svg` (`style.css`) makes them pick up the same `color`-driven hover/active/disabled states and light/dark theming as every other icon in the app, without adding a font dependency. If a future icon needs the exact Material Symbols shape and isn't in the vendored font, follow this same pattern (inline SVG with the real path data, not a substitute glyph) rather than guessing a similarly-named classic-icon replacement.
- **`#secondToolbar`** (the small "Editing Route/POI/Area" + End/Cancel pill shown while `measureTool` is active) is generated entirely by `showSecondToolbar(elementId)`/`hideSecondToolbar()` in `ui.js` — there's no static markup for it in `app.php` beyond the empty `<div id="secondToolbar">`. It deliberately mirrors `#editToolbar`'s exact pill styling (`border-radius`, `padding`, `box-shadow`, same `.second-toolbar-icon`/`.toolbar-icon-btn` sizing) and reuses the same three SVG path strings (kept as the `TOOLBAR_ICON_SVG` lookup at the top of `ui.js`, duplicated from `app.php` since one is static markup and the other JS-generated). Its horizontal position is **not** a fixed CSS offset — `showSecondToolbar()` reads `#editToolbar`'s live `getBoundingClientRect().width` and sets `#secondToolbar`'s `right` to `editToolbarWidth + 10 (editToolbar's own right offset) + 8 (gap)` on every show, so it always sits a fixed 8px to editToolbar's left regardless of how many/which buttons editToolbar ends up rendering. Don't hardcode that offset — if editToolbar's button count or padding ever changes, this recalculation keeps the gap correct automatically.
- **`#tourModeBadge`** (the "Tour Mode" pill shown on the main map while a tour is active, `tour.js`: `activateTourMode()`/`exitTourMode()`) is deliberately left-aligned under `#sidemenu-toggle`/`.map-search-wrapper` (`top:64px; left:16px`) rather than centered — a centered badge would sit directly under `#editToolbar` on the opposite corner and read as crowding it. Tour Mode is just a route filter on the normal map (`RouteController::index()`'s existing `?tour_id=` support), not an overlay, so `#editToolbar` stays fully visible and usable while it's shown — don't route it through `panelOpened()`/`panelClosed()`, which is for actual full-screen panels. Its `z-index: 5` is deliberately below `.cookiemenu`'s (10) and `#sidemenu`'s, so opening any panel or the drawer naturally covers it with no extra JS needed, the same way `#editToolbar` would need explicit hiding but this doesn't. The route InfoWindow (`route.js`: `showRouteInfoWindow()`) also gets a small "Option C" shortcut next to its existing edit-pencil icon — a `playlist_add` icon that toggles `#addToTourMenu`, a short list of the user's own tours (from the same `tours[]` global `tour.js`'s `getToursByUserId()`/`getPublicTours()` and `tour-admin.js` use) plus a "+ New tour…" row that opens the Tours panel's create form. It's a convenience layered on top of the Tours panel's own "Edit Routes" checklist (`tour-admin.js`: `manageTourRoutes()`), not a replacement for it — building a new multi-route tour from scratch is still better done there.
- User-admin-panel markup uses its own `.admin-user-form` / `.adminFormRow` / `.adminFormLabel` / `.adminFormField` classes rather than the POI/Route/Area edit-window's `.infoWindowElement`/`.leftCol`/`.rightCol`, so styling one doesn't affect the other.
- Custom checkboxes app-wide rely on a CSS rule that hides the real `<input type="checkbox">` and renders a Material-icon glyph via `::before` on an immediately-following sibling `<label>` (see `input[type="checkbox"] + label::before` in `public/css/style.css`) — the `<label>` must be the checkbox's next DOM sibling or the checkbox becomes invisible with no fallback rendering. The POI-visibility toggles in the nav drawer deliberately opt out of this: `<label class="nav-toggle-row"><input type="checkbox">...<span class="nav-switch-track">...</span></label>` wraps the checkbox instead of following it, so the generic glyph rule doesn't match and a separate pill-switch look (`.nav-switch-track`/`.nav-switch-thumb`, driven by `:checked ~` sibling selectors) applies instead.
