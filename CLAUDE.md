# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

YTAN is a web app for planning kayak touring trips (POIs, routes, tours, areas on a map). It's a from-scratch rebuild of an older app called PESR, structured so a future native mobile client can talk to the same backend. See `README.md` for the full "notable differences from PESR" list (REST API replacing a `service.php?cmd=...` RPC dispatcher, JWT bearer auth replacing PHP sessions, a path-traversal fix in `WsiRenderer`, etc.) and `docs/API.md` for the REST API reference.

## Tracking work (todo.md)

The repo-root `todo.md` is the running record of feature work and notable fixes on this project — every new feature and every larger change must be noted there automatically, without the user having to ask. It's split into two top-level sections: `# Offene Punkte` (open items, still pending) at the top, and `# Erledigt` (done) at the bottom — each item is its own `##` heading. A still-open request stays under `# Offene Punkte`; once it's done, move its heading down into `# Erledigt` (don't leave finished work under "Offene Punkte", and don't leave a stale open item sitting below a done one). A closed item's body follows the existing style: the original request struck through (`~~...~~`) followed by `Gelöst (YYYY-MM-DD): ...` with a substantive explanation of what was actually built/fixed — not just "done", enough detail that the *why* and *how* survive independently of git history.

## Commands

```bash
composer install
cp .env.example .env              # fill in DB credentials, JWT_SECRET, MAPS_API_KEY, MAIL_*, APP_URL
php bin/migrate.php               # applies database/migrations/*.sql in filename order, tracked in a schema_migrations table
php -S localhost:8000 -t public public/index.php
```

- Adding a schema change: add a new plain-SQL file `database/migrations/NNN_description.sql` (zero-padded, next number) — there is no migration framework, just `bin/migrate.php` running un-applied files in sorted order once each.
- No frontend build step — `public/js/*.js` are plain scripts loaded directly by `templates/app.php`, no bundler/transpiler/package.json.
- This machine has multiple PHP installs; the composer.json requires PHP >=8.1 but a plain `php` on PATH may resolve to an older 7.x build. Prefer an explicit 8.1+ binary (e.g. `/c/dev/php8/php.exe` on this Windows box) for anything version-sensitive (composer, migrations, `php -l`).
- When testing a UI/frontend change in a browser, always check the **mobile viewport first** (e.g. ~390×844), then desktop — this app is Mobile First (see Frontend architecture below), and mobile-only problems (touch targets too small, overlapping fixed-position elements, responsive fallbacks not kicking in) are easy to miss if desktop is checked first or exclusively.
- **Auto-generated build version**: `composer install`/`composer update` run `git config core.hooksPath .githooks` (a `post-install-cmd`/`post-update-cmd` script), which activates `.githooks/pre-commit` — a plain shell script (works under Git Bash on Windows too) that regenerates the repo-root `VERSION` file (`YYYYMMDDHHMM-<short hash of the parent commit>`, UTC) and `git add`s it into the very commit being made, every commit. `src/App.php`'s `/` route reads it (`$appVersion`, falls back to `'dev'` if the file is missing) and `templates/app.php` shows it in the nav drawer just under the Legal list. `VERSION` sits outside `public/` (never web-accessible, like `.env`) but isn't excluded from `bin/deploy.bat`'s upload package, so the deployed copy (no `.git` there) still has a real value to read. If you clone fresh and the hook doesn't seem to fire, re-run `composer install` or set `core.hooksPath` by hand.
- **Scheduled cleanup task**: `php bin/cleanup-weather-data.php` deletes `weather_forecast` rows older than 7 days (todo.md's "Wetterdaten" item) — the first recurring/cron-style task in this project, so nothing invokes it automatically; add your own cron entry (or systemd timer) on each deployed host, e.g. `0 3 * * * /usr/bin/php /path/to/ytan/bin/cleanup-weather-data.php >> /path/to/ytan/storage/logs/weather-cleanup.log 2>&1`. A location's *previous* forecast is already deleted the moment a fresh one is fetched (`WeatherForecastRepository::upsert()`'s `ON DUPLICATE KEY UPDATE` on the `(lat, lng)` unique key) — this script only catches rows nobody has re-fetched at all, which would otherwise sit forever.
- **Second scheduled cleanup task**: `php bin/cleanup-file-caches.php` deletes stale files from `storage/geocoding-cache` and `storage/static-maps-cache` (todo.md's "Cache-Bereinigung" item), the two disk caches with no cleanup routine of their own — same "nothing invokes it automatically" situation, add your own cron entry, e.g. `0 3 * * * /usr/bin/php /path/to/ytan/bin/cleanup-file-caches.php >> /path/to/ytan/storage/logs/file-cache-cleanup.log 2>&1`. The actual deletion logic lives in `FileCacheCleanupService::cleanDirectory()` (age-based, by file mtime) so it's unit-testable independent of the CLI wrapper; the per-directory retention window comes from each cache's own service class (`GeocodingService::CACHE_TTL_SECONDS`, the same age its own `readCache()` already treats as a miss; `StaticMapImageService::CACHE_MAX_AGE_SECONDS`, a disk-retention window rather than a freshness TTL, since those images are content-addressed and never go stale on their own). `storage/weather-cache` is deliberately out of scope — that data moved into the `weather_forecast` DB table above, the directory itself is now unused. `storage/{area,poi,route,tour}-images` are also out of scope — persistent user uploads, not a cache, already deleted through their own delete endpoints.

## Testing

There is a real PHPUnit suite (`tests/Unit/`, `tests/Integration/`) backed by a **dedicated test database** — never the live one.

**One-time (or after a schema change) setup:**
```bash
composer test-db    # = php bin/setup-test-db.php
```
This clones the *structure* (no data) of whatever database your `.env`'s `DB_DATABASE` points at into a sibling `<name>_test` database (so `ytan` → `ytan_test`), then marks every migration file currently in `database/migrations/` as already applied there. It exists because `001_create_core_schema.sql` and a few other early migrations were deleted from the repo at some point (the live dev DB still has the tables they created; `bin/migrate.php` alone can no longer recreate them from scratch) — cloning the live structure sidesteps that gap entirely, whatever it currently contains becomes the test DB's baseline. Re-run it whenever the schema changes outside of a normal `bin/migrate.php` run picking up a new file for the test DB too (e.g. after a manual schema tweak, or to refresh the clone's baseline).

**Running the suite:**
```bash
composer test        # = phpunit, uses phpunit.xml + tests/bootstrap.php
```
`tests/bootstrap.php` loads the real `.env` for host/credentials but forces `DB_DATABASE` to `<name>_test` before anything else runs — even a buggy test can't reach the real database. `tests/TestCase.php` wraps every test method in a transaction that's rolled back in `tearDown()`, so tests never need their own cleanup and never see another test's leftover rows regardless of order; use its `createUser()`/`createRoute()`/`authPayload()` fixture helpers rather than hand-rolling inserts. Controller tests (`tests/Integration/ControllerTestCase.php`) call a `*Controller` method directly with a constructed PSR-7 request (`Slim\Psr7\Factory\*`) rather than going through Slim's router/`AuthMiddleware` — close enough to a real request for a controller's own logic (permission checks, validation, response shape), without a running HTTP server; an `ApiException` a controller throws propagates straight to the test, which is exactly what `expectException()` wants.

**This suite must be run after every change** (`composer test`), not just spot-checked manually — it already caught a real bug within minutes of being written (`TourRepository::setTags()`'s tag-casing dedupe kept the *last* casing seen instead of the documented *first*). When you add or change backend logic (a repository method, a controller endpoint, a permission rule), add or update a test for it in the same change — don't leave coverage for later. Manual/browser testing (see the mobile-first rule above) is still expected for anything UI-facing.

**Frontend end-to-end tests (Playwright)**: `tests/e2e/` is a self-contained Playwright project (its own `package.json`/`node_modules`, separate from both PHPUnit and the repo-root `package.json`'s Capacitor tooling) covering the frontend flows PHPUnit can't reach: login, POI/Route/Area creation via real map clicks, right-click context menus, and Tours (create + add a route). One-time setup: `cd tests/e2e && npm install && npx playwright install chromium`. Run with `npm test` (or `npm run test:headed` to watch it, `npm run test:ui` for Playwright's interactive UI mode).

- **Isolation from real dev data, and from PHPUnit's own `ytan_test`**: tests run against their own `ytan_e2e` database, created automatically on first run (`tests/e2e/seed/reset-e2e-db.php` clones it from `ytan_test`'s structure the same way `bin/setup-test-db.php` builds `ytan_test` itself) — never the real `ytan` dev DB, and deliberately **not** the same database PHPUnit uses either. `tests/e2e/server/e2e-router.php` is a router wrapper around `public/index.php` used only by `playwright.config.js`'s `webServer`, which forces `$_ENV['DB_DATABASE'] = 'ytan_e2e'` before `App::create()` ever runs. A plain OS environment variable override (`DB_DATABASE=ytan_e2e php -S ...`) does **not** work for this — verified empirically: `Dotenv::createImmutable()->load()` populates `$_ENV` from `.env`'s file value whenever `$_ENV` itself doesn't already hold the key, which is true here even when the OS env var is set (`getenv()` sees it, `$_ENV` doesn't, a `variables_order` quirk) — only setting `$_ENV` directly, before `Dotenv` runs, sticks. **Sharing `ytan_test` with PHPUnit was tried first and broke it**: leftover e2e-created rows (a POI landing on an auto-increment id a PHPUnit fixture inserts explicitly, an extra `user` row skewing `count()`-based assertions, `poitype` rows a fixture assumes don't exist yet) failed 12 PHPUnit tests the next time `composer test` ran - a completely separate database was the fix, not more cleanup logic.
- **Test user**: `tests/e2e/global-setup.js` runs `reset-e2e-db.php` once before the whole suite — upserts a fixed `e2e_test_user` (full rights, so the suite tests the *flows* rather than re-testing PHPUnit's own permission coverage), copies `poitype` reference rows from the real dev DB (schema-only clones have none), and wipes anything that user created on a *previous* e2e run. It does **not** clean up between individual tests within one run — specs that need a guaranteed-empty patch of map to click on explicitly re-center there first (see below), rather than relying on the database being empty.
- **`fitToPoiBounds()` gotcha**: `map-core.js` unconditionally re-centers the map to `GET /pois/bounds` on load, which spans *every* POI in the database with no scope filter (`PoiRepository::bounds()` has no `WHERE`) — within a single e2e run this means "the center of the map" silently shifts depending on what earlier specs already created. `fixtures.js`'s `settleMapAt(page, lat, lng, zoom)` forces a known center/zoom (set twice, since `fitToPoiBounds()`'s own fetch can resolve after the first call and clobber it) — any spec that clicks the map at a fixed pixel offset must call it first, at coordinates not used by any other spec.
- **POI marker click offset**: a POI's `Marker` only sets `icon: {url}`, no explicit `anchor` — Maps' default anchor for a plain-URL icon is the *bottom-center* of the image, not its visual middle, so right-clicking exactly at a marker's `LatLng` pixel lands just below the icon on the empty map underneath (see `context-menu.spec.js`'s POI test, offset up by half the vendored icon's height).
- **Map click timing**: two `page.mouse.click()` calls fired back-to-back at different pixels can collapse into a Maps `dblclick` (which zooms instead of adding a second vertex) — `route.spec.js`/`area.spec.js` wait ~400ms between clicks so Maps' own click/dblclick disambiguation treats them as separate.
- **Desktop right-click, not the touch long-press path**: POI/Route/Area context menus register a native `contextmenu` listener directly (`poi.js`/`route.js`/`area.js`) *and* a separate touch-only long-press fallback (`attachLongPressContextMenu()`/`findLongPressTarget()` in `map-core.js`, for browsers where a long-press doesn't reliably translate to a `contextmenu` event) — `context-menu.spec.js` drives the former (`page.mouse.click(..., {button: 'right'})`), which is what a desktop user actually triggers; it doesn't exercise the touch fallback.
- Not yet covered: the touch long-press path itself, and cross-browser (only the `chromium` project is configured — add `firefox`/`webkit` to `playwright.config.js`'s `projects` if that coverage is ever needed).

## Backend architecture

- **Framework**: Slim 4, PSR-7 (`slim/psr7`). No DI container — everything is wired by hand in `src\App.php`'s `App::create()`: PDO connection, repositories, services and controllers are constructed and closed over directly, then routes are registered as flat `$app->get/post/put/delete(...)` calls (no route groups).
- **Autoloading**: PSR-4, `Ytan\` → `src/`.
- **Request flow**: `public/index.php` → `App::create($rootDir)->run()`. `AuthMiddleware` runs globally and decodes a `Bearer` JWT (if present) into the PSR-7 request attribute `"auth"` — it never rejects a request itself, so every route sees either a decoded payload or `null` there.
- **Controllers** (`src/Http/Controllers/*Controller.php`) extend `BaseController`, which provides:
  - `json($response, $data, $status=200)` — wraps success payloads as `{"data": ...}`.
  - `requireAuthUser($request)` — 401s if `auth` attribute is null, else returns the JWT payload array.
  - `requireAdmin($request)` — like above, plus 403s unless `is_admin` is true on the payload.
  - `assertOwnerOrAdmin($authUser, $ownerId)` — 403s unless the caller owns the resource or is admin.
  - `jsonBody($request)` — decoded JSON request body as an array.
- **Errors**: `src/Exception/*` (`ApiException` base + `NotFoundException`/`ValidationException`/`UnauthorizedException`/`ForbiddenException`) carry an HTTP status; the error handler registered in `App::create()` turns any thrown `ApiException` (or Slim's own HTTP exceptions) into `{"error": {"message": ...}}` with that status, plus a `trace` array when `APP_DEBUG=true` and the status is 500.
- **Data access**: `src/Domain/{Area,Poi,Route,Tour,User}/*Repository.php` take a raw `PDO` via constructor injection and use plain `prepare()`/`execute()`/`fetch()`/`fetchAll()` — no query builder/ORM. `Connection::fromEnv()` (`src/Database/Connection.php`) builds the PDO instance from env vars.
- **Auth/JWT**: `AuthService` (`src/Service/AuthService.php`) issues and verifies JWTs (`firebase/php-jwt`), holds the password policy (`validatePasswordFormat`), and login/self-change/admin-set/invite-token-redemption all funnel through a shared private `issueToken()` so the JWT claim shape (`sub`, `username`, `email`, `firstname`, `lastname`, `is_admin`, `tour_create`, `tour_publish`, `tour_manage`, `tour_copy`, `route_view_recording`, `iat`, `exp`) stays consistent everywhere a token is minted.
- **Granular Touren rights**: `user.tour_create`/`tour_publish`/`tour_manage`/`tour_copy` (flat boolean columns, same convention as `is_admin` — no permissions table) gate tour creation, publishing, managing any user's tours, and copying respectively; `is_admin` always overrides all four. `BaseController::assertTourRight($authUser, $right)` checks one; `TourController`'s private `assertCanManageTour()`/`assertCanPublishTour()` compose the "admin/tour_manage OR (owner AND the specific right)" rule used by update/delete/publish/route-membership/image endpoints. Granting/revoking happens in the admin user form (`admin-user.js`); `UserController::index()`/`UserRepository::findAll()` accept the same field names as exact-match query-param filters for the admin panel's filter chips. Because a partial `PUT /users/{id}` body must never blank out fields it didn't mean to touch, `UserRepository::update()` merges `$data` onto the existing row before writing (learned the hard way — an early manual test with a 2-field payload wiped a real user's name).
- **`route_view_recording` right**: same flat-boolean-column convention as the Touren rights above, but not a Touren right itself — it gates *visibility* of a GPS-recorded route's `recorded_at`/`recording_duration_seconds`/`recorded_by_username` (see `RouteRepository::SELECT_WITH_RECORDER`, a `LEFT JOIN user` for the recorder's username) rather than any action. `BaseController::hasRight($authUser, $right)` is the non-throwing counterpart to `assertTourRight()` — `true`/`false` instead of a 403 — for exactly this "redact a field, don't block the request" shape; `RouteController::redactRecordingInfo()` uses it on every response-producing endpoint (`index`/`show`/`create`/`update`) and fully `unset()`s the three keys rather than nulling them, so a caller without the right can't distinguish "not recorded" from "recorded, but hidden from you" — this applies even to the recording's own owner. `route.js`'s `showRouteInfoWindow()` mirrors the same check client-side (defense in depth: `saveRoute()`'s optimistic local route object still carries these fields in memory right after a save, before any server round-trip would have redacted them).
- **Tour tags/photos**: `tour_tag` (simple `tour_id`+`tag` join table, not a delimited string column) via `TourRepository::setTags()`/`getTags()`/`getTagsForTours()` (the last one bulk-fetches for list/search results, avoiding N+1). Photos (`tour_image` table + files under `storage/tour-images/{tourId}/`, outside the public webroot) go through `TourImageService` (validates real file bytes via `finfo`, not the client's claimed MIME type; max 5 MB, max 8/tour) and are served back through `GET /tours/{id}/images/{imageId}` after the same visibility check as the tour itself (public, owner, or admin/tour_manage) — never a static, guessable URL, since a photo can belong to a private tour. Because a private image needs the caller's Bearer token and a plain `<img src>` can't send one, the frontend fetches it as a Blob (`api-client.js`'s `fetchBlob()`) and sets `img.src` to an object URL (`tour-admin.js`'s `renderTourImage()`) instead of pointing `<img>` at the endpoint directly.
- **Tour route-change notifications & captcha-gated delete**: `RouteController::update()`/`delete()` look up affected tours via `TourRepository::findByRoute()` and recalculate each one's cached `total_length` (this is the *third* total_length trigger, alongside `TourController`'s own add/remove/reorder-route endpoints — a route's length changing via the normal route editor is easy to forget to wire up). `TourNotificationService` emails each affected tour's creator on change/delete (and the route's owner if a public route got deleted) via three new plain-text `MailService` methods, following the app's existing single-recipient `send()` pattern; every send is try/caught so a mail failure (e.g. no reachable SMTP in dev) never fails the underlying route update/delete. Deleting a route that belongs to ≥1 tours additionally requires a captcha: the first `DELETE` (no/invalid `captcha_token`+`captcha_answer` query params) throws `CaptchaRequiredException`, which `App::create()`'s error handler merges into the JSON error body as `tour_count`/`captcha:{question,token}`; `CaptchaService` signs the challenge as a JWT (reusing `JWT_SECRET`, since this stateless-JWT app has no PHP session to hold it server-side) scoped to `"route:{id}"` so it can't be replayed against a different route. Frontend: `route.js`'s `removeRoute()` catches the 422, shows `confirm-dialog.js`'s `showCaptchaDialog(question)`, and retries the same `DELETE` with the answer attached.
- **User invite / password-reset tokens**: `user_token` table (single-use, `purpose` = `invite` or `reset`, expiry-checked in SQL) backs both the admin-invite-new-user flow and "forgot password" — both resolve through the same `/set-password?token=...` landing page (`templates/set-password.php`), which is server-rendered (not part of the SPA) since it must work for a signed-out visitor arriving from an email link. `MailService` (`src/Service/MailService.php`, PHPMailer/SMTP) sends those emails; SMTP + `APP_URL` (needed to build absolute links outside of a request context) come from env vars.
- **Subdirectory deployment**: the app can be served from a path prefix (e.g. `http://localhost/ytan/public/`) instead of a vhost root. `App::create()` derives `$baseUrl` per-request from `$_SERVER['SCRIPT_NAME']` and calls `$app->setBasePath()`; that same `$baseUrl` is threaded into `templates/*.php` and injected client-side as `window.YTAN_API_BASE` (`public/js/api-client.js` reads it, falling back to `/api/v1`). Don't hardcode absolute paths in templates/JS — always go through `$baseUrl` / `window.YTAN_API_BASE`.

## Frontend architecture
- Mobile First
- Plain ES6, no bundler. `templates/app.php` loads vendor libs then `public/js/*.js` in a fixed, load-order-dependent `<script>` sequence (`config.js → helper.js → api-client.js → settings.js → ui.js → toast.js → confirm-dialog.js → nav-menu.js → map-core.js → poi.js → route.js → area.js → tour.js → tour-admin.js → user.js → admin-user.js`) — later files rely on globals (`log`, `LOG_ERROR`/`LOG_WARN`/`LOG_INFO`/`LOG_DEBUG`, `user`, `map`, `settings`, `Ytan`, etc.) defined by earlier ones, and most functions are attached implicitly to `window` rather than namespaced.
- **API access**: all backend calls go through the `Ytan` singleton (`public/js/api-client.js`): `Ytan.get/post/put/del(path[, body])`, `Ytan.isLoggedIn()`, `Ytan.setToken/getToken` (JWT kept in `localStorage['ytan_token']`, not a cookie). Don't `fetch()` the API directly from feature code.
- **Session bootstrap**: on page load (`templates/app.php`'s inline `<script>`), `user` is set to `initUser()`'s empty shape first, then — if a token exists — revalidated against `GET /api/v1/auth/me` (rather than trusting a cached `sessionStorage['user']` blindly) before the UI reflects logged-in state.
- **Navigation drawer** (`#sidemenu`): a hamburger-toggled drawer. Opening and closing use two separate, differently-positioned buttons, matching the approved mockup: `#sidemenu-toggle` (fixed top-left, always shows the `menu` glyph, calls `toggleMenu()`) sits outside the drawer and only opens it; a `.nav-close-x` button lives *inside* the drawer's `root` screen (`.nav-brand-row`, pushed to the row's right edge via `margin-left:auto`, next to the "YTAN" wordmark) and only closes it. `#sidemenu`'s z-index (11) is deliberately higher than `#sidemenu-toggle`'s (10) so the open drawer visually covers the hamburger button instead of the two overlapping — don't reintroduce an icon-swap or reposition the toggle to "fix" that overlap, the z-index order is the fix. Only the `root` screen has a close-x; submenu `.nav-screen`s rely on their own `arrow_back` button instead. The drawer itself contains a stack of `.nav-screen` panels (`public/js/nav-menu.js`: `navMenuGoTo(screenId)`/`navMenuBack()`/`navMenuReset()`) that slide horizontally instead of one flat list. Screens are matched by `data-nav-screen="..."` in `templates/app.php`; closing the drawer resets the stack back to `root` (delayed until `#sidemenu`'s own 0.5s slide-out transition finishes, so the reset is never visible mid-close). Map type/units/POI-visibility checkboxes/tour selector all kept their exact IDs when they moved into this structure (`settings.js`'s `saveSettings()`/`loadSettings()` and a couple of direct references in `area.js`/`route.js` read them by hard-coded `getElementById`, independent of DOM position) — never rename `detail0`-`detail16`, `detailroutes`, `detailareas`, `detailwsi`, `maptype1`-`maptype3`, or `unit1`-`unit2` without updating those too. The `pois` screen also has `selectAllPois()`/`selectNonePois()` (`map-core.js`) wired to a `.nav-quick-actions` chip pair. The `preferences` screen holds both the Appearance (Light/Dark, `setTheme()`) and Units (Metric/Nautical, `editUnit()`) segmented controls, one above the other — Units used to be its own `map-settings` screen but was folded in here since both are simple app-wide toggles; it also shows a live-updating `.nav-example-card` (`updateUnitExample()`, `map-core.js`) that mirrors the current unit choice, right below the Units control. The login/logout/change-password UI lives inside this same `preferences` screen — `showUserWindow()`/`closeUserWindow()` (`user.js`) call `navMenuGoTo()`/`navMenuBack()` instead of toggling their own visibility. The admin user-management UI does **not** live in the drawer — see the full-screen panel below; the drawer's `site-settings` screen just has a single "Users" row that opens it via `openUserAdminMenu()`.
- **Full-screen overlay panels** (cookie consent, Impressum/Datenschutz, admin user management, the Tours panel): all four share one CSS pattern — a `<div class="cookiemenu">` slid in via a `style.width` transition (`0` ↔ `100%`), plus a matching `openXMenu()`/`closeXMenu()` JS function pair (see `openCookieMenu`/`openLegalMenu` in `public/js/ui.js`, `openUserAdminMenu`/`closeUserAdminMenu` in `admin-user.js`, `openTourAdminMenu`/`closeTourAdminMenu` in `tour-admin.js`). The admin panel is triggered from the drawer's "Site Settings" screen but is deliberately its own full-screen panel rather than a nested `.nav-screen` — a data table doesn't fit the ~320px drawer width — so `openUserAdminMenu()` calls `closeMenu()` first for a clean transition. `openTourAdminMenu()` (triggered directly by the drawer root menu's "Tours" row — unlike POIs/Preferences there's no intermediate `.nav-screen` for it; the old in-drawer tour-picker dropdown that used to live there was removed as obsolete once this panel could do everything it did, and `openTourAdminMenu()` calls `closeMenu()` itself, same as `openUserAdminMenu()`) follows the same pattern, swapping its single `#touradminmenu-body` container's content between four sub-views — list/search (name/description/creator text search plus a length-range filter, all client-side over the already-loaded `tourAdminAllTours`), detail (tags, photo gallery, routes, and an action row whose buttons are individually gated by `canManageTour()`/`canPublishTour()`/`canCopyTours()`; a "Share" button sits alongside them, gated on `tour.public == 1` instead since `TourController::show()` has no `assertCanView()` of its own the way `showImage()`/`document()` do — `shareTour(id, name)` mirrors `map-core.js`'s `shareMap()` Web Share API/clipboard-copy pattern, building a `?tour={id}` link that `initMap()` reads the same way it already reads `z`/`lat`/`lng`, fetching the tour directly and calling `tour.js`'s `activateTourMode()` once the map is ready — or a `showToast()` notice if the tour 404s, e.g. deleted or made private since the link was shared), create/edit form (name/description/tags always; a photo upload grid only in edit mode, since a tour needs an id before it can own photos), and a route-membership manager ("Option B" from the Touren feature design: a searchable checklist of the user's own routes, with an "in this tour" section reordered via up/down buttons rather than drag-and-drop) — the same way `admin-user.js` swaps `#useradminmenu-list`/`#useradminmenu-form`. The "New tour" button and the map InfoWindow popup's "+ New tour…" shortcut (`route.js`) are both gated on `canCreateTours()`. `openCookieMenu()`/`openLegalMenu()` do the same for the same structural reason: `#sidemenu`'s z-index (11) sits above `.cookiemenu`'s (10) so the drawer, if left open, visually covers whatever panel opens on top of it — every "open a full-screen panel from inside the drawer" trigger must call `closeMenu()` first, not just the admin one. Every open/close call also goes through the shared `panelOpened()`/`panelClosed()` counter in `ui.js`, which hides `#editToolbar` (it visually sits above these panels) while any panel is open — use that pair rather than toggling it directly, since the counter is what keeps two panels opened back-to-back from clobbering each other's close. Each panel also ends its own `.cm_content` with a `<div class="panel-logo">` — deliberately a normal flow element, not `position: fixed`, since a fixed logo stays pinned to the same screen position for as long as the panel is open and covers whatever content scrolls underneath it, not just content past the very end. New panels should follow this same pattern (including their own trailing `.panel-logo`) rather than introducing a new one. `.panel-logo` and `.logo_large` (the same YTAN mark shown on the pre-consent GDPR screen) are empty `<div>`s, not `<img src="images/ytan.svg">` — the SVG is applied via `mask-image` with `background-color: var(--color-text)`, the same technique used for the Google InfoWindow close button's icon (see the "Google Maps InfoWindow chrome" block in `style.css`). This lets the logo, which is pure hardcoded black inside the SVG file itself, follow the theme instead of staying invisible on a dark panel. Because a `<div>` has no intrinsic size the way an `<img>` would, both classes set an explicit `aspect-ratio` matching the SVG's own `viewBox` (1873/1349) — don't drop that when touching either rule, or the mask collapses to zero height. `#legalmenu` (the Imprint/Privacy Note panel) is shared by a third row too: "About" (right above Imprint in the drawer's footer list) calls the exact same `openLegalMenu('<baseUrl>/about')`/`closeLegalMenu()` pair, fetching `templates/about.php` via the `/about` route (`src/App.php`) the same way `/legal/impressum` and `/legal/datenschutz` serve their templates — no dedicated JS function or panel of its own. Its content is the text that used to sit as a plain `#disclaimer` block at the bottom of the root menu screen. Follow this pattern (a new `templates/*.php` + route, opened via the existing `openLegalMenu(url)`) for any other static text that belongs alongside Imprint/Privacy Note, rather than special-casing the panel.
- **Dark mode / design tokens**: `public/css/style.css` defines its palette as CSS custom properties on `:root` (light) and `:root[data-theme="dark"]` (dark) — `--color-bg-panel`, `--color-text`, `--color-accent`, etc. Every color in the stylesheet should go through one of these tokens rather than a literal, or it will only render correctly in one theme. The active theme is `settings.theme` ('light'/'dark'), persisted through the same settings-cookie mechanism as `maptype`/`unit` (`saveSettings()`/`loadSettings()` in `settings.js`), applied via `document.documentElement.dataset.theme` by `setTheme()` (`map-core.js`, next to `editMapType`/`editUnit`) and switched from a segmented control in the "Preferences" drawer screen. `applyStoredTheme()` (`settings.js`) is called as the very first thing in `templates/app.php`'s inline bootstrap script, before Google Maps even starts loading, so a returning dark-mode user doesn't see a flash of the light theme. The standalone pages (`impressum.php`, `datenschutz.php`, `set-password.php`, `forgot-password.php`) load the same `style.css` and so get the light palette automatically, but have no theme-switch UI of their own — out of scope by design, they're not SPA screens. CSS custom properties can't be substituted inside a `url()` data-URI's own content (see `.select-css`'s dark-mode arrow icon override) — those need a full second `background-image` declaration with the color hardcoded, not a `var()` inside the SVG string. The Route/POI/Area edit dialogs (`.infoWindowElement`, opened via `google.maps.InfoWindow`) are a second exception: Google renders the bubble chrome itself (background, tail, close button, scrollbar) via its own stylesheet injected at runtime (`.gm-style-iw-c`, `.gm-style-iw-tc::after`, `.gm-ui-hover-effect span`), completely outside our `--color-*` cascade — our own markup inside the bubble already picks up the right tokens, but the chrome around it stayed hardcoded white until explicit `:root[data-theme="dark"] .gm-style-iw-c { ... !important }`-style overrides were added (see the "Google Maps InfoWindow chrome" block in `style.css`, right after the MeasureTool section). `!important` is required there since Google's rules load after ours. If a future Maps API version renames these classes, that block is the place to fix it.
- **Fonts**: self-hosted (`public/fonts/`, declared in `public/css/fonts.css`) — Plus Jakarta Sans (body, replaces the old Roboto) and Sora (headings/brand, replaces the old Roboto Condensed), both fetched from Google Fonts once and vendored the same way `MaterialIconsRound` already was (no Google Fonts CDN requests at runtime, matching the "everything local" approach). `--font-body`/`--font-display` custom properties point at them.
- **Icon font**: `.material-icons-round` uses a vendored, older/classic Material Icons glyph set (`public/fonts/MaterialIconsRound-Regular.*`), not the newer Material Symbols set — some newer icon names (e.g. `key`, `route`, `pentagon`, `polyline`, `hexagon`) don't exist in it and silently render as nothing (no visible glyph, no error). When adding an icon, verify the ligature name is actually present in the vendored font rather than assuming current Material Symbols naming. The mockup itself isn't a reliable source for ligature names either — it renders icons with "Material Symbols Rounded" pulled live from Google Fonts, a different (larger, newer) font the app deliberately doesn't depend on at runtime (see "everything local" below).
- **`#editToolbar`'s three create-buttons** (`routeButton`/`poiButton`/`areaButton`) are the one exception to the icon-font approach above: they render the mockup's exact `route`/`add_location`/`pentagon` Material Symbols Rounded glyphs as inline `<svg viewBox="0 -960 960 960"><path fill="currentColor" .../></svg>` markup directly in `templates/app.php`, not via the vendored icon font (`route`/`pentagon` don't exist there — see above). `fill: currentColor` on `.toolbar-icon-btn svg` (`style.css`) makes them pick up the same `color`-driven hover/active/disabled states and light/dark theming as every other icon in the app, without adding a font dependency. If a future icon needs the exact Material Symbols shape and isn't in the vendored font, follow this same pattern (inline SVG with the real path data, not a substitute glyph) rather than guessing a similarly-named classic-icon replacement.
- **`#secondToolbar`** (the small "Editing Route/POI/Area" + End/Cancel pill shown while `measureTool` is active) is generated entirely by `showSecondToolbar(elementId)`/`hideSecondToolbar()` in `ui.js` — there's no static markup for it in `app.php` beyond the empty `<div id="secondToolbar">`. It deliberately mirrors `#editToolbar`'s exact pill styling (`border-radius`, `padding`, `box-shadow`, same `.second-toolbar-icon`/`.toolbar-icon-btn` sizing) and reuses the same three SVG path strings (kept as the `TOOLBAR_ICON_SVG` lookup at the top of `ui.js`, duplicated from `app.php` since one is static markup and the other JS-generated). Its horizontal position is **not** a fixed CSS offset — `showSecondToolbar()` reads `#editToolbar`'s live `getBoundingClientRect().width` and sets `#secondToolbar`'s `right` to `editToolbarWidth + 10 (editToolbar's own right offset) + 8 (gap)` on every show, so it always sits a fixed 8px to editToolbar's left regardless of how many/which buttons editToolbar ends up rendering. Don't hardcode that offset — if editToolbar's button count or padding ever changes, this recalculation keeps the gap correct automatically.
- **`#tourModeBadge`** (the "Tour Mode" pill shown on the main map while a tour is active, `tour.js`: `activateTourMode()`/`exitTourMode()`) is deliberately left-aligned under `#sidemenu-toggle`/`.map-search-wrapper` (`top:64px; left:16px`) rather than centered — a centered badge would sit directly under `#editToolbar` on the opposite corner and read as crowding it. Tour Mode is just a route filter on the normal map (`RouteController::index()`'s existing `?tour_id=` support), not an overlay, so `#editToolbar` stays fully visible and usable while it's shown — don't route it through `panelOpened()`/`panelClosed()`, which is for actual full-screen panels. Its `z-index: 5` is deliberately below `.cookiemenu`'s (10) and `#sidemenu`'s, so opening any panel or the drawer naturally covers it with no extra JS needed, the same way `#editToolbar` would need explicit hiding but this doesn't. The route InfoWindow (`route.js`: `showRouteInfoWindow()`) also gets a small "Option C" shortcut next to its existing edit-pencil icon — a `playlist_add` icon that toggles `#addToTourMenu`, a short list of the user's own tours (from the same `tours[]` global `tour.js`'s `getToursByUserId()`/`getPublicTours()` and `tour-admin.js` use) plus a "+ New tour…" row that opens the Tours panel's create form. It's a convenience layered on top of the Tours panel's own "Edit Routes" checklist (`tour-admin.js`: `manageTourRoutes()`), not a replacement for it — building a new multi-route tour from scratch is still better done there.
- User-admin-panel markup uses its own `.admin-user-form` / `.adminFormRow` / `.adminFormLabel` / `.adminFormField` classes rather than the POI/Route/Area edit-window's `.infoWindowElement`/`.leftCol`/`.rightCol`, so styling one doesn't affect the other.
- Custom checkboxes app-wide rely on a CSS rule that hides the real `<input type="checkbox">` and renders a Material-icon glyph via `::before` on an immediately-following sibling `<label>` (see `input[type="checkbox"] + label::before` in `public/css/style.css`) — the `<label>` must be the checkbox's next DOM sibling or the checkbox becomes invisible with no fallback rendering. The POI-visibility toggles in the nav drawer deliberately opt out of this: `<label class="nav-toggle-row"><input type="checkbox">...<span class="nav-switch-track">...</span></label>` wraps the checkbox instead of following it, so the generic glyph rule doesn't match and a separate pill-switch look (`.nav-switch-track`/`.nav-switch-thumb`, driven by `:checked ~` sibling selectors) applies instead.
