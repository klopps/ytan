## Capacitor-App-Hülle für Android

~~Baue mir eine App auf Basis von Capacitor.~~ Gelöst (2026-09-14): Anlass war die vorangegangene Diskussion, dass verlässliche Hintergrund-GPS-Routenaufzeichnung mit einer reinen Web-App/PWA auf Android/iOS nicht möglich ist (Browser drosseln `watchPosition()` bei gesperrtem Bildschirm/App im Hintergrund) - einzige verlässliche Lösung ist eine native App-Hülle mit echter Betriebssystem-Hintergrund-Standort-Berechtigung. Details/Recherche/Fehlersuche siehe Projekt-Memory `project_capacitor_android_shell.md`.

**Grundgerüst** (neues `package.json`/`node_modules`/`android/` im Repo-Root, zusätzlich zur bestehenden PHP-App, die weiterhin ohne Build-Schritt auskommt): `@capacitor/core`/`android`/`cli` (v8.5.2), App-ID `org.pesr.ytan`. **Live-URL-Modell** statt gebündeltem Snapshot: `capacitor.config.json`s `server.url = "https://test.pesr.org/"` - die WebView zeigt die echte, deployte Seite, da `templates/app.php`s `$baseUrl`/`window.YTAN_API_BASE` serverseitig pro Request gerendert wird (`src/App.php`) und unter einem gebündelten lokalen Ursprung falsch gewesen wäre. Plugin `@capacitor-community/background-geolocation` (MIT, kostenlos - bewusst nicht das scheinbar besser gepflegte, aber kostenpflichtige Capawesome-Pendant). Neue, vorläufige `public/js/capacitor-bridge.js` als reiner Nachweis-Hook (`capacitorBridgeStartTestWatch()`), no-op außerhalb der nativen Hülle.

**Zwei wichtige, live verifizierte Config-/API-Fallstricke gefunden und gefixt**: (1) `android.useLegacyBridge: true` muss gesetzt sein, sonst stoppen Hintergrund-Updates nach 5 Minuten (direkt aus der Plugin-Doku, nicht angenommen). (2) In genau diesem Legacy-Bridge-Modus liefert `addWatcher()` die Watcher-ID entgegen der eigenen TypeScript-Doku synchron als String statt als Promise - live am echten Gerät per Chrome DevTools Protocol diagnostiziert und defensiv gegen beide Formen abgesichert. Außerdem: `window.Capacitor.registerPlugin` existiert zur Laufzeit gar nicht (nur ein Bundler-Import-Helfer) - native Plugins landen automatisch unter `window.Capacitor.Plugins.<Name>`.

**Toolchain auf der Entwicklungsmaschine**: Java 17 (Temurin) + Android Studio (bringt SDK mit) installiert. Live-Korrektur unterwegs: Java 17 reicht für das Android Gradle Plugin, aber Capacitor 8s eigene Android-Library verlangt JDK 21 (`sourceCompatibility JavaVersion.VERSION_21`, direkt im Plugin-`build.gradle` bestätigt) - gelöst ohne Zusatzinstallation über Android Studios eigenes eingebettetes JDK (`Android Studio\jbr`, Version 25). `gradlew assembleDebug` läuft seitdem durch.

**Echter Beweis auf echter Hardware**: APK auf einem Android-13-Xiaomi-Gerät installiert (MIUI blockierte die adb-Installation - `INSTALL_FAILED_USER_RESTRICTED` - Workaround: `adb push` ins Downloads-Verzeichnis + manuelle Installation über den Dateimanager, umgeht die Sperre komplett). Watcher gestartet, Bildschirm gesperrt, Handy vom Rechner getrennt und ca. 7 Minuten bewegt. Beim Wiederverbinden zeigte Chrome DevTools (spielt beim Neu-Attachen an eine durchgehend laufende Seite den kompletten Konsolen-Verlauf ab - nützlicher Nebenfund) drei echte Standort-Updates aus der Trennzeit (18:20:23, 18:22:16, 18:23:05 - reale, unterschiedliche Koordinaten mit 3-4m Genauigkeit, passend zur Bewegung). Die letzte Meldung liegt 6:15 Minuten nach der letzten bekannten Verbindung - über die 5-Minuten-Grenze hinaus, bestätigt also gezielt den `useLegacyBridge`-Fix. Die App-Instanz lief die ganze Zeit durch, ohne von Android/MIUI beendet zu werden.

Die eigentliche Aufzeichnen-Funktion/UI (Punkte sammeln, als Route speichern, mit dem Backend synchronisieren) ist bewusst noch nicht gebaut - das wäre ein eigener, späterer Punkt.

## Regenradar-Layer

~~Gibt es Regenradar-Daten kostenlos im Netz, die zeigen wo es gerade regnet und die eine Prognose für die nächsten Minuten oder Stunden macht?~~ Gelöst (2026-09-13): **RainViewer** (rainviewer.com) als Datenquelle - kostenlos, kein API-Key, live per `curl` bestätigt inkl. `Access-Control-Allow-Origin: *`, daher bewusst **kein** Backend-Proxy (anders als Weather/Geocoding) - der kleine `weather-maps.json`-Metadaten-Call und die eigentlichen Kachelbilder gehen beide direkt vom Browser aus. Liefert ~2 Stunden echten Radar-Verlauf in 10-Minuten-Schritten (`radar.past`); eine Kurzfrist-Prognose ist im kostenlosen Endpunkt aktuell leer/undokumentiert und wird daher bewusst nicht versprochen - nur "wo es eben geregnet hat", kein Nowcast.

Neuer Toggle "Regenradar" in der Drawer-POIs-Screen (`detailradar`, gleiches Muster wie der WSI-Toggle), neues eigenständiges Modul `public/js/radar.js`. Aktiviert eine `google.maps.ImageMapType`-Kachelebene über `map.overlayMapTypes`; eine neue Kontrollleiste unten-mittig (`#radarControls`) bietet Play/Pause, einen Zeitschieberegler über alle geladenen Frames, eine "vor X Min."-Anzeige und den pflichtgemäßen RainViewer-Attributionslink.

**Wichtiger, live verifizierter Fund während der Umsetzung**: RainViewers kostenlose Kacheln enthalten nur bis etwa **Zoomstufe 7** echte Daten - ab Zoomstufe 8 liefert der Server für jede Koordinate dieselbe (per md5sum bestätigt identische) "Zoom Level Not Supported"-Platzhalterkachel mit HTTP 200, unabhängig von x/y. Die für diese App normale Kajaktour-Zoomstufe (12-16) liegt weit darüber. `google.maps.ImageMapType`s `maxZoom`-Option klemmt die an `getTileUrl()` übergebene Zoomstufe entgegen der Erwartung **nicht** automatisch (live mit einer instrumentierten Testebene bestätigt: Maps ruft weiterhin mit der echten, näheren Zoomstufe auf). Echtes "Overzoom" (client-seitiges Zuschneiden/Hochskalieren der nächstgelegenen unterstützten Kachel) wäre bei diesem extremen Zoomunterschied (bis zu 128-fach) ohnehin nur ein nahezu einfarbiger, wertloser Block gewesen - deshalb stattdessen bewusst die einfachere, korrekte Lösung: `getTileUrl()` liefert oberhalb von Zoomstufe 7 `null` (Maps zeigt dann gar keine Kachel statt der Platzhaltergrafik), und ein `zoom_changed`-Listener blendet die Zeitleisten-Kontrollen zwischen Zoomstufe >7 und ≤7 gegen einen Hinweistext ("Zum Anzeigen des Regenradars weiter herauszoomen") um. Live geprüft: bei Zoomstufe 14 keine Platzhalterkachel sichtbar, nur der Hinweis; ab Zoomstufe 6 erscheinen echte Regenflächen.

## Service-Worker Cache-Bug (2026-09-12)

Nach Umschalten der Sprache (EN→DE) zeigte die About-Seite weiterhin den alten Text - ein normales Reload (F5) half nicht, erst Ctrl+F5 zeigte schließlich Deutsch. Ursache: `sw.php`s Fetch-Handler behandelte bislang JEDEN Same-Origin-Request cache-first, nicht nur die statischen Shell-Assets (JS/CSS/Icons) - eine dynamische, vom Cookie abhängige Seite wie `/about` wurde beim ersten Laden dadurch dauerhaft im Cache Storage eingefroren und nie wieder neu geladen, unabhängig vom Browser-eigenen HTTP-Cache (den ein `fetch(..., {cache:'no-store'})` umgangen hätte - der Service Worker fängt den Request aber schon vorher ab). Behoben: der Fetch-Handler cached jetzt nur noch Requests mit statischen Datei-Endungen (`.js`/`.css`/`.png`/`.svg`/`.webmanifest`/...), alles andere (auch künftige neue Routen) geht immer ins Netz. Zusätzlich räumt die `activate`-Phase bereits bestehende Fehlcache-Einträge automatisch auf, sodass auch schon betroffene Browser sich selbst heilen, ohne dass Nutzer manuell die Website-Daten löschen müssen. Live per Playwright verifiziert (Cache-Inhalt vor/nach dem Fix direkt inspiziert, das gemeldete Szenario in beide Richtungen nachgestellt).
